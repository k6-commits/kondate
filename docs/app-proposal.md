- 作成日：2026年11月8日
- 前提資料：[research-report.md](research-report.md)（市場調査レポート）
- 読み方：1〜4章で全体がわかる（約5分）。5章以降は作る人向けの詳細。専門用語は末尾の[用語集](#用語集)にまとめた。

## 1. 結論：何を作るか

**仮称「きめとく」― うちの献立当番**

> 献立を「作る」AIではなく、「回す」AI。
> 家族がふだん食べている定番料理を覚えて、買い物日に合わせて平日の夕食と買い物リストを先に決めておく。何もしなければそのまま確定し、予定が崩れたら1タップで組み直す。

- **対象**：日本の共働き・子育て世帯で、平日の夕食を主に決めている人とそのパートナー
- **入口**：LINE公式アカウント（友だち追加だけで始められ、パートナーも同じ献立と買い物リストを見られる）
- **約束**：平日の夕食の半分以上が、自分で考えずに決まる状態にする（目標は、考える日を週1日以下にすること）。出発点は、検証の最初の週に日誌で測る。

**LLMの使い方**

- LLMは裏方に徹する。担当は次の3つ。
  - 話し言葉や写真を、アプリが扱えるデータに直す
  - ルールを満たした候補の中から、その家庭に合う献立を選ぶ
  - 理由を一言で添える
- アレルゲンの判定と、分量・買い物リストの計算は、LLMに任せずコード（辞書・ルール・計算）で行う。判定できない物は「要確認」として止める。
- **アプリは除外の補助で、アレルギーの安全を保証するものではない。** この一文は画面にも出す。

## 2. なぜこのアプリか（調査からの根拠）

| 調査でわかったこと | だからこうする |
|---|---|
| 負担の中心は「作る」より「決める」こと。共働き家庭の女性に平日夕食の負担を聞くと、「献立を考える」が87.0%で、2018年度より増えた（JR東日本企画。[2-1](research-report.md#2-1-つらいのは決めること)） | レシピを探す道具ではなく、決める役を引き受ける道具にする。成功指標も「閲覧数」ではなく「考えずに済んだ夕食の数」にする |
| 「アプリが失敗するのは、脳がしたくない毎日の決定を増やすから」（r/ADHD）。選択肢が多いと固まる、という事業者の聞き取りもある | 毎日2〜3案から選ばせない。1案を既定にし、何もしなければ確定する。触るのは例外のときだけ |
| 多くの家庭は定番を回している。米国では86%が同じ料理を繰り返していると答えた（HelloFresh※）。献立サービスDinner SolvedのTim Masterson氏は、家庭が回している料理は10〜15品ほどだと述べている | 「うちの定番帳」を中心に組み、新しい料理は週1〜2品だけ混ぜる |
| ChatGPTに献立を丸投げすると、特売や買い物の予定と合わない、という指摘がある（利用者のブログ。買いに行く予定のない食材が献立に入る例）。固定の計画は生活とずれて破綻する | 家庭の状態（定番・買った物・作った物・家族の反応）を持ち続け、崩れたら組み直す。買い物中に「鶏むねが安い」と書けば、その週を組み替える |
| 子育て中の共働き世帯では、惣菜・冷凍食品・宅食に罪悪感がある人が72.9%（冷凍宅配食の会社の調査※）。別の調査では、料理の手間を減らすことを81.5%が支持した（博報堂生活総研） | 冷凍食品・惣菜の「ラク日」を、最初から正規の献立として組み込む |
| 「食事の献立を考える」を自分でしているのは、妻97.7%、夫36.7%（大和ハウス、2017年）。献立アプリが「女性の管理対象を一つ増やすだけ」になるという指摘もある（Washington Post） | 夫婦が同じ献立とリストを持ち、差し替えや買い物を分担できるようにする |
| LLMの献立には、アレルゲンの混入（2023年のChatGPTで56件中4件）や、栄養量の系統的なずれが報告されている。データベースとルールの検証で改善したという報告もある（開発者自身の小規模な評価） | 判定と計算はコードで行い、LLMにはルールを満たした候補からしか選ばせない。効果は自社の評価セットで確かめる |
| 米国App Storeの8アプリの低評価では、価格・課金の壁への言及がアプリ平均で36% | 中核の機能は無料にし、強制トライアルをしない |
| 海外では献立サービスの閉鎖が続いた。スーパーに買われたMealimeは、その自社アプリに吸収されて閉鎖した。AI献立から家族向けのAIアシスタントに広げたOllieは、汎用AIアシスタントの参入で資金調達が難しくなり、閉鎖した | 献立の「生成」ではなく「運用」で勝負する。特定の小売に依存せず、汎用AIと幅で競わずに、家庭の状態を深く持つ |
| 日本のApp Storeの売上上位はレシピメディア。献立を主な機能とするアプリの最高は36位だった。ただし、献立機能を持つレシピ保存アプリ（CookGo 7位、レピッタ13位）や、無料のme:newは使われている | 「献立を回す」ことに特化した定番は、日本ではまだ見当たらない。空きなのか、お金が払われにくい領域なのかは、検証の年額前払いで確かめる |
| 日本の食品の買い物は店が中心（ネットスーパーはスーパー売上の1.1%）。頻度は家庭によって違う（週1〜2回36.3%、週3〜4回33.1%、ほぼ毎日22.6%。mitoriz※） | 店で買う前提の買い物リストを中核にする。買い物日は複数指定できるようにし、ネット注文との連携は後回しにする |

## 3. 誰のためのアプリか

**主なターゲット**

- 首都圏など都市部の、共働き・子育て世帯（子どもは未就学〜小学生）
- 平日の夕食の献立を主に決めている人（多くは母親）と、買い物や調理を分担するパートナー
- 週に数回は自炊していて、作れる定番はある。けれど毎日決めるのがつらい

**このターゲットを選ぶ理由**

1. 「献立を決める負担」を示すデータが最も厚く、時間の制約も強い層だから。
2. 日本の献立の形（主菜・副菜・汁物、旬、弁当、まとめ買い、冷凍）に合わせて作り込むことが、海外勢や汎用AIに対する差になるから。
3. 家族で使うので、乗り換えには夫婦の合意が要る。これが防御になる。

**専業主婦・主夫の世帯について**：アプリはそのまま使える。ただし最初の募集と訴求は、共働き世帯に絞る（専業主婦に絞った最近の調査は見つからなかった）。

**後から広げる層**

- 単身・学生（少量・節約）
- 高齢の親がいる世帯（減塩、やわらかさ）
- アレルギーのある家庭（取り分け）
- 健康目標がある人（たんぱく質など）

いずれも、中核の仕組み（定番帳・エンジン・検証層）が育ってから広げる。

## 4. どんな体験か（ある家庭の1週間）

以下は、MVPの有料版での例。無料版との違いと、後の段階の機能には印を付けた。買い物日は日曜（まとめ買い）と水曜（買い足し）とする。

**土曜の夜（日曜の買い物日の前夜）**　担当者のLINEに届く（無料版は、メニューの「今週の献立」を押すと表示される）

```
きめとく：来週の夕食です。何もしなければ、このまま確定します。
  月 鮭のホイル焼き／小松菜のおひたし／豆腐とわかめの味噌汁（25分）
  火 豚こまと白菜の味噌炒め／卵スープ（20分）
  水 ラク日：冷凍ぎょうざ／もやしナムル（10分）
  木 鶏の照り焼き／キャベツの塩もみ（25分）※鶏ももは日曜に買って冷凍
  金 カレー／サラダ（35分）
  先週は5日のうち4日、考えずに済みました。いちばん人気は鶏の照り焼きでした。
  [買い物リストを開く]  [差し替えたい日を選ぶ]
```

- **買い物リスト**
  - 売り場順に並び、人数分に換算され、パック単位に丸めてある。
  - 日曜の分と水曜の分に分かれている。
  - 夫婦どちらのスマホからでもチェックでき、チェックした物は「家にある物」として記録される。
- **差し替え**：その日について、別の案を2つだけ示す。

**火曜の夕方**　有料版は「今日はこれ」が届く。無料版は、メニューの「今日のごはん」を押す。

```
きめとく：今日は豚こまと白菜の味噌炒め（20分）。白菜を使い切るなら今日がおすすめです。
  [作った]  [別のに]  [今日は無理]
→ [今日は無理]
きめとく：了解です。今日はラク日にして、冷凍うどんと卵でどうでしょう。
         豚こまと白菜は明日に回し、冷凍ぎょうざは次のラク日に使います。
         豚こまは消費期限を確かめて、明日までに使えなければ今夜冷凍してください。
  [OK]  [ほかの案]
```

**水曜の買い物中**　献立グループに書き込む

```
@きめとく 鶏むねが安い
きめとく：木曜の鶏の照り焼きを、鶏むねに替えますか？ 鶏ももは冷凍のまま来週に回します。
  [替える]  [そのまま]
```

**水曜の夜（有料）**

```
きめとく：明日の鶏の照り焼き用に、鶏ももを冷凍室から冷蔵室へ移しておいてください。
```

**食後**

- 家族の反応を◎○△で1タップ記録する。子どもの分は親のスマホから入力する。
- ◎の料理は出番が増え、△の料理はしばらく出ない。
  - 無料版：世帯全体の反応で学習する。
  - 有料版：一人ひとりの好みを学習する。
- 子どもは翌週の候補に2択で投票できる（親のスマホから。無料）。

**ポイント**

- 有料版では、自分から操作するのは「差し替え」「今日は無理」「反応」の3つの例外だけ。無料版は、これに加えて、メニューから「今週の献立」「今日のごはん」を開く。
- チャットは必須ではない。献立グループで「@きめとく 水曜は夫が飲み会」「@きめとく 卵切れた」と書けば、人数や在庫の変更として受け取る。
- 後の段階で加わるもの：
  - 夕食を多めに作って翌日のお弁当に回す（第2段階・有料）
  - カレーの甘口を先に取り分ける（第3段階）

## 5. 機能

### 5-1. MVP（第2〜4か月の3か月で作るもの）

**必須**

| # | 機能 | 中身 |
|---|---|---|
| 1 | **数分で始める** | 3つの質問と、定番料理5〜10品で、今週の残りの日の献立を出す |
| 2 | **うちの定番帳** | 料理名だけの得意料理、冷凍食品、惣菜を同じ扱いで登録できる。定番ごとに「うちの材料メモ」（豚か牛か、など）を持てる |
| 3 | **週の献立エンジン** | 買い物日を起点に、平日の夕食を組む。何もしなければ確定し、差し替えは2択 |
| 4 | **正確な買い物リスト** | 集約・換算・丸めをすべてコードで計算する。売り場順に並べ、夫婦で同期する |
| 5 | **今日のごはん／今日は無理** | 当日の献立を返し、「作った／別のに／今日は無理」を1タップで記録する。**無料で回数制限なし** |
| 6 | **家族の反応と子どもの投票** | ◎○△の記録と、子どもの2択投票（親のスマホから） |
| 7 | **信頼の土台** | 除外食材・アレルゲンを辞書とルールで判定し、わからない物は「要確認」と表示する。データはいつでも書き出せる |
| 8 | **有料の仕組み** | 担当者への配信、一人ひとりの好みの学習、3人目以降の参加。Web決済、カード登録不要の2週間トライアル、更新前の通知、解約 |

**各機能の補足**

- **1（初回の質問）**：家族の人数と年齢帯、除外食材・アレルギー、買い物の曜日（複数可）。料理名は話すか打つかで入力し、LLMが標準料理マスタと照合する。ユーザーは確認するだけ。音声は、スマホのキーボードの音声入力を使う（自前の文字起こしは作らない）。
- **3（エンジンの条件）**
  - 主菜＋副菜または汁物
  - 週内の偏り（和洋中・肉魚）、旬、除外条件
  - 新しい料理は週1〜2品、ラク日は週1日
  - 買い物日が複数あるときは、週1回の計画で全日分を組み、買い物リストを買い物日ごとに分ける。
- **4（買い物リストの計算）**：人数換算、単位の統一（個とg）、同じ食材の集約、パック単位への丸め、常備調味料の除外。
- **5（今日は無理）**：冷凍・惣菜・5分メニューに差し替え、使わなかった生鮮を傷みやすい順に翌日以降へ回す。除外食材のある世帯では、確かめ済みの定番を優先して差し替える。

**β版で足すもの（第5か月〜）**

- 外部レシピの取り込み：利用者が貼ったURLやスクリーンショットから、料理名と材料の候補をLLMが取り出す（8章のルールに従う）。
- 除外食材の目安チェック：取り込んだレシピの材料に、登録した除外食材がないかを調べる。結果は「見つかった」か「見つからなかった（要確認）」の2つだけで、「大丈夫」とは表示しない。

**MVPのために用意するデータ**

- **標準料理マスタ（約300品）**：主菜／副菜／汁物の区分、主なたんぱく源、ジャンル、旬、標準の材料と分量（何人分か）、アレルゲン、作り方の出典。LLMで下書きし、人が検証する。
- **食材マスタ**：単位換算、パックの量、売り場、アレルゲン（派生原材料を含む。例：小麦→醤油）、傷みやすさの目安日数。

**新しい料理の出どころ**：作り方の本文はアプリが持たない。新しい料理は、次の3つから選び、作り方は出典のページへ案内する。

1. 利用者が登録した外部レシピ
2. 提携先のレシピ
3. 標準料理マスタのうち、作り方の出典がある料理

**MVPで作らないもの**：ネイティブアプリ、写真からの在庫登録、特売データ連携、栄養の数値表示、ネットスーパーとの連携。

### 5-2. 第2段階（β版で4週間の継続率60%以上を確かめた後）

- **レシートや注文画面の取り込み**：レシート、生協・ネットスーパーの注文画面のスクリーンショットから、買い物リストを自動で消し込み、在庫を補正する。合計額で照合し、自信のない行だけ確認してもらう。画像は読み取ったら削除する。
- **1食あたりの実際の食費と使い切りの週報**：物価高の中で、節約の実感が続ける理由になる。
- **弁当・子どもの昼食・夏休みなど長期休暇のモード**
  - 夕食を多めに作って翌日に回す。傷みやすい料理は回さない。
  - 夏休みに子どもの「今日のお昼ごはん何？」が負担だという母親は65.4%（パナソニック※）。
- **予算と特売のモード**：地域スーパーや生協と組む。チラシデータの公開APIは見つかっていないので、業務提携が前提になる。
- **生協の宅配との併用**：生協の注文内容を取り込み、店での買い物と合わせて計画する。

### 5-3. 第3段階

- **共通のベース料理と取り分け・後のせ**：カレーは甘口を先に取り分ける、麻婆豆腐は豆板醤を入れる前に分ける、など。子ども・高齢の親・減量中の人に対応する（1歳未満は対象外。8章）。
- **アレルギーのある家庭向けのモード**：法務設計と管理栄養士の監修をそろえてから出す。
- **減塩・たんぱく質の目安表示**：日本食品標準成分表で計算し、管理栄養士が監修する。
- **汎用AIとの接続**：ChatGPT、Claude、Geminiから「我が家の献立台帳」を参照・更新できる接続口（MCP）を作る。入口を汎用AIに取られても、データの持ち主であり続けられる。
- **企業向けの提供**：生協・地域スーパーに、献立エンジンを提供する（中立性のルールは8章）。

## 6. 既存アプリ・汎用AIとの違い

| | 大手レシピアプリ（クックパッド、クラシル、デリッシュキッチン） | 新興の献立アプリ（献立AI Plat、レピッタなど） | me:new | 汎用AI（ChatGPT、Gemini、LINE「Agent i」） | 海外の小売AI（Instacartなど） | **きめとく** |
|---|---|---|---|---|---|---|
| 中心にあるもの | 自社レシピの検索・保存（献立機能もある） | レシピ保存、献立、買い物リスト | 自社レシピからの自動献立 | その場の相談とレシピ生成 | 自社の店での購入 | **家庭の定番と状態（在庫・反応・予定）** |
| 決める回数 | 自分で選ぶ | アプリによる | 少ない | 頼むたびに決める | 少ない | **最小（既定で確定）** |
| 崩れたとき | 自分で探し直す | アプリによる（Platは余る食材を警告） | 作り直し | 状況を説明し直す（好みを覚える機能は広がりつつある） | — | **1タップで組み直す** |
| 買い物リスト | あり（単位の表記が混ざるという声） | あり | レシピとリストで分量がずれるという声 | 在庫や予定と合わない例 | 自社の商品と結びつく | **コードで計算** |
| アレルゲン | 自分で確認 | 未確認 | 除外できる | 漏れる例が報告されている（2023年の研究で約7%。現行モデルは未検証） | 未確認 | **ルールで判定＋「要確認」（保証ではない）** |
| 家族 | 家族プランあり（デリッシュキッチン） | 家族で共有（Plat、レピッタ） | 家族グループ | 個人単位が中心 | 世帯 | **夫婦で分担、子どもも投票** |
| 中立性 | 自社レシピが前提 | 外部レシピの保存が中心 | 自社レシピが前提 | — | 自社の店が前提 | **他社レシピ・冷凍・惣菜も同じ扱い** |

**防御の考え方**：機能そのものは真似される前提で考える。

- 同じ月480円・年3,800円の献立AI Platは、推定1,000ダウンロード未満にとどまっている。機能や価格だけでは差がつかない。
- 差をつけるのは、使い続けてもらう仕組みである。真似しにくいのは次の4点。

1. **世帯ごとに貯まるデータ**：定番帳、家族の◎○△、調理の記録、推定在庫。使うほど当たるようになり、夫婦で使えば乗り換えには2人の合意が要る。
2. **中立性**：他社のレシピや冷凍食品・惣菜を同じ扱いにし、広告を出さず、「買いすぎない」を目標にする。自社レシピの閲覧・広告・購買データで稼ぐ大手には取りにくい立ち位置である。
3. **信頼**：除外の違反ゼロを目標にした検証、正確な買い物リスト、誠実な課金、データの持ち出し。
4. **小さく黒字にする**：レシピ制作や広告営業を持たない。資金調達に頼らない規模で回し、大手が本気で取りに来る前に定着させる。

## 7. LLMの使いどころと技術構成

### 7-1. LLMに任せること・任せないこと

| 処理 | 担当 | 理由 |
|---|---|---|
| 話し言葉の料理名を、標準料理マスタと照合する | LLM（確定は人） | 表記ゆれ（「ばあばの煮物」「うちの豚汁」）を吸収できる |
| 家族の書き込みを、変更の指示に直す（「水曜は夫いらない」→人数、「卵切れた」→在庫） | LLM | 入力の手間を減らす中心機能。あいまいなときは聞き返す |
| 週の組み合わせを選ぶ | **エンジンが候補を作り、LLMはその中から選ぶ** | 候補にない料理は出せない構造にして、条件違反を仕組みで防ぐ |
| 理由の一言（「月曜に買ったキャベツを使い切るため」） | LLM（事実はコードで照合） | 食材名や日付が実データにない文は、定型文に差し替える |
| 外部レシピから料理名・材料を取り出す（β版） | LLM（確定は人） | 画像や説明文を読むのはLLMの得意分野 |
| アレルゲン・除外食材の判定 | **コード（辞書とルール）** | 違反ゼロを目指す。わからない物は「要確認」で止める |
| 分量・単位換算・買い物リストの集約・在庫の差し引き | **コード** | LLMに数値を作らせない |
| レシピの手順や分量 | **書かせない** | 定番は家族が作れる。新しい料理は出典のページへ案内する |
| 栄養の数値 | **MVPでは出さない**（後に成分表で計算） | 研究では、LLMの栄養推定は系統的にずれる |

### 7-2. 構成

```
LINE公式アカウント（Messaging API）＋ LIFF（LINE内で開くWeb画面）
        │   ※画面はWebで作り、後でPWAやネイティブアプリに移せるようにする
        ▼
API サーバー ── データベース（世帯、メンバーの年齢帯と除外、定番帳、
        │                       標準料理マスタ、食材マスタ、計画、買い物リスト、
        │                       推定在庫（たっぷり／少し／なし）、反応）
        ├── 献立エンジン（条件を満たす組み合わせを探すソルバ）
        ├── 検証層（除外・旬・多様性・分量を、生成の前後で全件チェック）
        └── LLM 層
              ・結果は決めた形式（JSONスキーマ）で受け取り、機械的に検証する
              ・選べるのは候補IDのリストだけ
              ・失敗したら再試行し、それでも駄目ならエンジンだけで提案する
              ・登録した名前はIDに置き換えてから送る
```

- **夜間に週の計画をまとめて作る**
  - 応答は数秒以内で返す（海外の献立アプリには「生成に5分かかる」という指摘があった）。
  - 夜間のバッチ処理は完了まで最大24時間かかることがあるので、買い物日の2晩前に出す。間に合わなければ、エンジンだけで提案する。
- **評価セット**
  - 家族構成・除外・買い物日・崩れ方の組み合わせを数百ケース用意する。
  - モデルやプロンプトを変えるたびに、回帰テストとして流す。「全特定原材料×全料理」の除外判定テストも含める。
  - 最新の汎用LLMが同じテストでどれだけ違反するかも、定期的に測る。結果を公開するときは、モデルの版・日付・条件・件数を示し、客観的に確かめられる比較に限る。
- **在庫の扱い**
  - 在庫は3段階で持つ。
  - 無反応を「作った」とはみなさない。提案のときに「鶏むね、まだある？」と1問だけ確かめる。
- **データの出どころ**
  - 栄養計算には、文部科学省「日本食品標準成分表（八訂）増補2023年」を使う（第3段階）。
  - アレルゲンは、消費者庁の特定原材料等の最新リストに合わせて更新する。カシューナッツの表示義務は経過措置が2028年3月末まであるので、それまではカシューナッツが入りうる市販品を「要確認」にする。

### 7-3. モデルと費用の目安

Claudeを使う場合の例を示す（2026年10月時点の公開価格。実装時に公式ページで確認する。他社のモデルでも構成は同じ）。

| モデル | ID | 入力／出力（100万トークンあたり） |
|---|---|---|
| Claude Opus 5.5 | `claude-opus-5-5` | $4／$20 |
| Claude Sonnet 5.5 | `claude-sonnet-5-5` | $2／$10 |
| Claude Haiku 5.5 | `claude-haiku-5-5` | $0.10／$0.50 |

**有料1世帯・1か月あたりの概算**

前提（1ドル＝150円）：

- 週の計画：月4.3回。1回あたり入力8,000・出力3,000トークン（思考を含む）。
- 書き込みの解釈：月30回。1回あたり入力2,000・出力600トークン。
- リンクの取り込み：月5回。1回あたり入力5,000・出力800トークン。
- 合計：入力約11.9万・出力約3.5万トークン。

| 使うモデル | 1世帯・1か月あたり |
|---|---|
| すべて Opus 5.5 | 約1.18ドル（約180円） |
| すべて Sonnet 5.5 | 約0.59ドル（約90円） |
| すべて Haiku 5.5 | 約0.03ドル（約4円） |

**補足**

- 「今日は無理」と差し替えは、エンジンだけで処理するので計上していない。
- 出力が想定の2倍になると、費用は約1.6倍になる。実際の使用量は、コンシェルジュ検証で測る。
- 無料版では、週の計画をエンジンだけで作り、書き込みの解釈だけに軽いモデルを使う。その場合、1世帯・1か月あたりの費用は約1〜5円になる。

**進め方**

1. まず最上位のモデルで品質の基準を作る。
2. 評価セットで品質が落ちないと確かめた処理から、軽いモデルに移す（料理名の照合や書き込みの解釈は、軽いモデルで足りる見込み）。
3. 週の計画は、夜間のバッチ処理（単価が半分）とプロンプトキャッシュを使って安くする。

## 8. 信頼と安全のルール

**アレルギー・除外**

- 判定はコード（辞書とルール）で行う。派生原材料（例：小麦→醤油）も辞書に持つ。
- 判定できない物は「要確認」にする。名前だけの定番、市販のルウ・調味料・冷凍食品（銘柄で原材料が違う）、店内で調理した惣菜などがこれにあたる。
- 表示が推奨にとどまる品目や、店内調理の惣菜には、アレルギー表示がないことがある。そのため、除外食材のある世帯には、惣菜・市販品を使う案を既定では出さない。出すときは「表示で確かめられない場合は、店やメーカーに確認を」と添える。
- アプリは除外の補助で、安全を保証しないと明示する。
- 重い食物アレルギー（アナフィラキシーの経験があるなど）と、医療的な食事療法（糖尿病・腎臓病など）は、MVPの対象外にする。アレルギーが入力されたときに、その旨と「医師の指示を優先してください」を表示する。
- 違反ゼロを目標に、全特定原材料×全料理の回帰テストを行う。

**乳幼児**

- 1歳未満の子は、献立の「食べる人」に含めない（人数換算・取り分けの対象外。離乳食はアプリの対象外）。
- 1歳未満の子がいる世帯には、はちみつと、はちみつを含む加工品を与えないよう注意を表示する（乳児ボツリヌス症）。
- 5歳以下の子がいる世帯には、豆・ナッツ類など、窒息の恐れがある食品の注意を表示する（消費者庁の注意喚起）。
- 子どもにとっての食べやすさや安全は、アプリでは判定しない（保護者が調整する）。

**食中毒**

- 生鮮は、パッケージの消費期限を優先する。期限を過ぎた物は使わないよう案内する。
- においや色では安全を判断できないと明記する。
- 作り置きの保存日数は、短めの目安として示し、根拠（公的な目安、管理栄養士の監修）を添える。

**危険な入力**

- 食品でない材料や、危険な組み合わせを求める入力は、入力の段階で止める（Pak'nSaveの事例）。

**レシピの権利**

- 取り込みは、利用者が貼ったURLやスクリーンショットを、利用者の依頼で1回だけ処理する。
- 取得の方法は、各サービスの規約で認められたものに限る。SNSは、利用者が撮ったスクリーンショットを使う。
- 本文・手順・写真は保存しない。材料と分量は、利用者が確かめてから「うちの材料メモ」として保存する。
- 出典名とリンクを常に表示し、元のページへ送客する。外部への公開・共有はしない。
- 法務の確認と料理家への聞き取りは、MVPの開発を始める前（第4週まで）に行う。

**個人情報**

- アレルギーなど健康に関わる情報は、要配慮個人情報に当たり得るものとして、取得時に明示的な同意を得る。
- 子どもについて保存するのは、年齢帯・ニックネーム・除外食材・反応だけ。
- 登録した名前は、IDに置き換えてからLLMに送る。
- 自由に書かれた文には、名前や健康の情報が含まれ得る。そのため、送った内容を学習に使わず、保存期間が限られる契約のLLM事業者を選ぶ。
- 海外の事業者にデータを送ることは、プライバシーポリシーに書き、同意を得る。
- LINEのボットは献立専用のグループにだけ入り、「@きめとく」を付けた発言だけを解釈する。それ以外の発言は受信時に捨て、ログにも残さない。

**課金**

- 価格を最初に示す。強制トライアルもカードの先行登録もしない。
- 更新前に通知し、すぐ解約できるようにする。
- データはいつでもCSV／JSONで書き出せる。
- サービスを終了するときは移行期間を設けると、規約に書く。

**中立性と提携**

- 提携や送客の有無で、家庭の献立の候補や順番を変えない。
- 提携先の商品を出すときは、提携であることを表示する。
- 食品メーカーからは送客料を受け取らない。メーカーとの取引は、相手のサービスにエンジンを提供することに限る。

**AIの表示**

- AIが選んだことと、その理由を一言で示す。
- AIの機能を使わなくても、エンジンだけで献立が回るようにする。

## 9. ビジネスモデル

### 9-1. 無料と有料の線引き

| | 無料 | 有料「当番プラン」 | 提供の時期 |
|---|---|---|---|
| 週の献立と買い物リスト | ○（メニューから開く） | ○（担当者に配信） | MVP |
| 夫婦2人での共有、除外食材の指定、複数の買い物日 | ○ | ○ | MVP |
| 今日のごはん／今日は無理（その場の組み直し） | ○（回数制限なし） | ○ | MVP |
| 反応の記録と子どもの投票（親のスマホから） | ○（世帯全体で学習） | ○（一人ひとりの好みを学習） | MVP |
| 定番帳・リンク登録 | 30品まで | 無制限 | MVP（リンクはβ版） |
| LINEでの配信 | なし（応答のみ） | 担当者1人に配信：平日夕方の「今日はこれ」、解凍が要る日の前夜、週の献立 | MVP |
| 3人目以降の参加 | — | ○ | MVP |
| 弁当・昼食・長期休暇、レシート取り込み、予算・特売 | — | ○ | 第2段階 |

**線引きの考え方**

- 決める負担の中心（週の献立から買い物リストまで）と、困った瞬間の「今日は無理」は無料にする。
- 有料にするのは、次の2種類。
  - 使える範囲を広げるもの
  - 配信の費用がかかるもの

**価格**

- 月480円、年3,800円。年額を主に勧める。
  - 理由：サブスクの1年継続率は、年額プランで28%、月額プランで8%（RevenueCat 2026年版。2024年に始まった購読）。
- カード登録不要の2週間全機能トライアルを用意する。

### 9-2. 収支の見立て

**前提**

- **LINEの通数**
  - 通数は「送信回数×受け取る人数」で数える。ユーザーのメッセージへの応答は通数に含まれない（[LINE Developers、2026年5月](https://developers.line.biz/ja/tips/2026/05/28/how-to-count-messages/)）。
  - 料金プランの無料通数を超えた分は、1通数円かかる（2026年10月に改定。実装時に[料金プランのページ](https://www.lycbiz.com/jp/service/line-official-account/plan/)で確認する）。
  - 以下では、1通1〜3円の幅で計算する。
- **有料版の配信**：担当者1人に月約34通。
  - 平日夕方の「今日はこれ」：22通
  - 解凍が要る日の前夜：約8通
  - 週の献立：約4通
- **決済**：Web決済の手数料を3.6%とする。LINEの中からの購入に、LINE・Apple・Googleの規約上の制限や手数料（15〜30%）がかかるかは、実装前に確かめる。

**1世帯・1か月の収支**

| | 無料 | 有料（年額） |
|---|---|---|
| 収入 | 0円 | 約317円（3,800円÷12） |
| 決済手数料 | — | 約11円 |
| LINE配信費 | 0円（応答のみ） | 約34〜102円（34通×1〜3円） |
| LLM費 | 約1〜5円 | 約4〜180円（軽いモデル〜最上位モデルだけ） |
| **差し引き** | **約−1〜−5円** | **約30〜270円** |

**読み方**

- 差し引きがいちばん小さいのは、1通3円で、最上位モデルだけを使う場合（約30円）。
- 配信を担当者1人に絞り、量の多い処理を軽いモデルに移せば、有料1世帯あたり月200円前後が残る。
- 無料版は応答とエンジンだけで回すので、1世帯あたりの費用は月数円に収まる。

**黒字化の目安**

- チームの固定費を年2,000万円と仮定する。有料1世帯あたり月200円（年2,400円）が残るなら、黒字化に必要なのは有料約8,300世帯。
- 実際には、使い続けている無料世帯の費用（月数円×世帯数）も加わるので、これより多く必要になる。

**獲得にかけられる費用**

- 粗利で見たLTV：年2,400円÷(1−0.28)で約3,300円（2年目以降も毎年28%が更新すると仮定）。
- 1人の獲得あたりの価値：LTV×有料への転換率。
  - 転換率2.9%なら約100円。
  - 2.9%は、ヘルス・フィットネス系のアプリで、ダウンロードから35日以内に有料になる人の中央値（RevenueCat）。献立アプリの値はなく、LINEの友だち追加は手軽なぶん、もっと低くなりうる（1%なら約33円）。
- このため、広告での獲得は成り立たない。

**獲得の経路**

- 世帯から世帯への紹介（保護者どうしの紹介特典など）
- 保育園・学童の保護者コミュニティ
- 「名もなき家事」をテーマにしたPR
- 外部レシピの取り込み（保存したまま作らないレシピを献立に変える）を入口にする

夫婦の招待は、新しい世帯は増やさないが、定着策として使う。

**第2の柱（第3段階）**

- 生協・地域スーパーへのエンジン提供。
- 生協の週1回の宅配は、買い物日を起点にした週計画と同じリズムで動く。
- 特定の1社には依存しない（スーパーに吸収されて閉じたMealimeの教訓）。

| **献立の有料サービスが日本で育っていない**（同じ価格の献立AI Platは推定1,000ダウンロード未満。クックパッドは有料会員が減少） | コードを書く前に、年額の前払いで支払い意思を確かめる。届かなければ、生協・小売向けの提供に軸を移す |
| **無料でも続かない例がある**（味の素「未来献立。」は約2年で終了） | 固定費を抑え、小さく黒字化する |
| **特売を見て売り場で決める家庭には、先に決めた献立が合わない**（売り場で決める人は35.5%） | 買い物中に「@きめとく 鶏むねが安い」と書けば、その週を組み替える（チラシのデータは要らない）。第0週の日誌で「売り場で献立を変えた回数」も測る |
| **最初の入力が面倒で離脱する** | 3問と料理名5〜10個で、数分で初回の献立を出す。在庫は手入力させない。所要時間の中央値を測る |
| **推定在庫がずれる** | 完璧な在庫管理は目指さない。在庫は3段階で持ち、提案のときに1問だけ確かめる |
| **アレルギーの事故** | コードでの判定、「要確認」、回帰テスト、対象外の明示（8章）。重いアレルギー向けのモードは、法務と監修をそろえてから |
| **LINE配信費やLLM費が想定を超える** | 9-2の前提をβ版で実測し、単価1〜3円で計算し直す。超えるなら、配信の回数や使うモデルを見直す |
| **料理家の反発** | 本文を保存せず、元のページへ送客する。将来は「作られた回数」のレポートや収益分配で味方にする |
| **LINEへの依存**（仕様・料金の変更） | 画面はWebで作り、PWAやネイティブアプリに移せるようにする |

## 12. 進め方（最初の5か月）

| 時期 | やること | 判断 |
|---|---|---|
| **第0週** | 首都圏の共働き・子育て世帯20〜30組を、Instagram広告と保護者のつながりで募る。1週間、日誌で基準値を取る（献立を考えた時間・迷った回数・「今日何？」と聞かれた回数・売り場で献立を変えた回数）。日本では、献立を考える時間や回数の最近の定量データが見つからなかった | — |
| **第1〜4週** | **コンシェルジュ検証**（コードはまだ書かない）。運営がスプレッドシート、LLM、人の目のチェックで週の献立と買い物リストを作り、LINEで送る。「今日は無理」は手で組み直す。別に、1週間ChatGPTかGeminiで献立を作ってもらう比較群を置く（継続率の集計には含めない） | — |
| **並行** | Instagram広告と事前登録ページで、3つの訴求と価格（3,800円・4,800円）を比べる。返金できる予約を数百件規模で集め、登録率と獲得単価を測る（訴求：献立を考えなくていい／使い切って買いすぎない／夫婦で分担できる） | — |
| **第4週まで** | 年額の前払いを募る（参考値。β版が始まるまでは、いつでも全額を返金する。特定商取引法の表示をそろえる）。法務の確認と、料理家5人ほどへの聞き取りを済ませる | **続行の目安**：提案の70%以上を作る、4週継続60%以上、考えた日数が半分以下、前払い5組以上、除外違反0件。届かなければ、平日3日分の版にする、ラク日の比率を変える、生協向けに軸を移す、などを試す |
| **第2〜4か月** | MVPを開発する（開発者2〜3人、管理栄養士は業務委託。デザインと検証は誰かが兼ねる）。標準料理マスタ約300品と食材マスタは、LLMで下書きして人が検証する。安全テストを整える。収まらなければ、開発期間を4〜5か月に延ばす | 除外違反0件がリリースの条件 |
| **第5か月〜** | 100〜300世帯でβ版を運用する。有料への転換率と、1世帯あたりのLINE＋LLM費を実測し、9-2の前提と比べる。最初の2週間の利用量が同じくらいの世帯どうしで、定番帳の◎の数と8週継続率を比べ、「蓄積が多いほど続く」かを確かめる | 転換率や費用が前提に届かなければ、価格と配信の設計を見直す。蓄積と継続の関係が出なければ、防御の前提を見直す |

## 13. 検討した別案

**比べ方**

- この提案は、1案だけで決めたものではない。
- 案は5つ。この提案書を書いたAIの最初の案（E）と、調査メモだけを渡した4つのAIエージェントがそれぞれ別の視点から作った案（A〜D）である。
- 採点したのは、利用者・事業戦略・開発と安全の視点を与えた別の3つのAIエージェント。
- 項目は6つ：痛みの大きさ、差別化・防御力、3か月でMVPを出せるか、日本での収益性、信頼・安全のリスクの低さ、LLMならではの価値。各10点（60点満点）で採点し、3つの平均を出した。
- **実際の利用者や専門家による評価ではない。** 人による確かめは、12章の検証で行う。採点の記録は [research-notes/design-panel.md](research-notes/design-panel.md) にある。

| 案 | 視点 | 中身 | 平均点 | 評価 |
|---|---|---|---|---|
| **B「うちの献立当番」** | 事業の防御力 | 中立な定番帳、決定論的なエンジン、世帯単位のサブスク、前払いでの検証 | **38.3** | 事業設計が最も堅い。ただし入口がネイティブアプリで、獲得と夫婦共有に壁がある。無料版で「今日は無理」が使えない点も問題とされた |
| **D「台所番」** | 技術 | レシートを撮るだけで家の食材が台帳になり、傷みそうな物から使い切る献立を出す | 35.7 | LLMの活用度は最大。しかし毎回のレシート撮影が前提で、台帳がずれやすい |
| **A「きめとく」** | ユーザーの痛み | LINEで週の献立が届き、何もしなければ確定。ラク日、子どもの投票 | 35.0 | 体験は最も良い。ただし無料版で毎日LINEに配信するため、利用者が増えるほど赤字になる |
| **C「おなじごはん」** | 取りこぼされた層 | 食物アレルギーの子がいても家族全員が同じ夕食を食べられる献立。共通ベースと取り分け | 31.3 | 差別化は強い。しかし見落とし1件で事業が終わる責任の重さと、市場の小ささが問題 |
| E「こんだて番」（最初の案） | — | 定番・在庫・特売・予定から毎日の献立を決める | 27.0 | 「突破口がない」「献立の組み合わせをLLMに任せている」「家族共有を有料にしている」と指摘された |

**3つの審査役の結論は一致した。**

- 土台にはAとBを統合する。体験と入口はAから、課金・防御・検証の設計はBから取る。
- Cの「取り分け」と「要確認」、Dの失敗時の設計を移植する。
- Dのレシート取り込みは、継続率を確かめた後に足す。

この提案書はその統合案である。最初の案への指摘（LLMに組み合わせを任せない、共有を有料にしない、狙いを絞る）も反映した。

その後、別のレビューで見つかった問題も直した。

- A案の「配信するほど赤字」の問題は、有料版の側にも残っていた。配信を担当者1人に絞り、9-2に収支表を加えた。
- 「保証」という言い過ぎの表現をやめた。

**別の方向として検討したもの**

- **SNSのレシピ保存アプリ**（海外のReciMe型）：課金の実績はあるが、日本ではクックパッドが同じ機能を出して炎上した。この提案では、単独のアプリではなく「定番帳への入口」として取り込む。
- **単身・学生向けの節約自炊アプリ**
  - ニーズはある。下宿生の食費は月29,853円で前年より増え、71.3%が食費を節約したいと答えた。
  - ただし大学生の生成AI利用は92.2%（無料版が中心）で、汎用AIで代わりが利きやすい。家族ほど防御も効かない。
  - 中核が育った後に、少量・節約のモードとして広げる。
- **写真でカロリーを計算するアプリ**（Cal AI型）：急成長した領域だが、献立とは別の市場で、競争も激しい。

## 用語集

| 用語 | 意味 |
|---|---|
| LLM | 大規模言語モデル。ChatGPTやClaudeのような、文章を理解・生成するAI |
| MVP | 最初に出す、最小限の機能の版 |
| β版 | 一部の利用者に先行して使ってもらう試用版 |
| KPI／北極星指標 | 成果を測る指標／その中でいちばん重視する指標 |
| LTV | 1世帯が解約するまでに払う金額の合計（ここでは費用を引いた粗利で計算） |
| コンシェルジュ検証 | アプリを作る前に、運営が手作業で同じサービスを提供し、使われるか・お金を払うかを確かめる方法 |
| LIFF | LINEの中で開くWeb画面の仕組み |
| PWA | ホーム画面に置けるWebアプリ |
| MCP | ChatGPTやClaudeなどのAIが、外部のサービスのデータを読み書きするための共通の接続方式 |
| ソルバ | 条件をすべて満たす組み合わせを探すプログラム |
| 回帰テスト | 変更のたびに同じテストを流し、前より悪くなっていないかを確かめること |
| トークン | LLMが文章を数える単位。料金はトークン数で決まる |
| プロンプトキャッシュ／バッチ処理 | 毎回同じ指示文を再利用して安くする仕組み／急がない処理をまとめて安く流す仕組み |
| JSONスキーマ | LLMの出力を、決めた形式のデータで受け取るための定義 |
| 要配慮個人情報 | 病歴など、取り扱いに本人の同意が必要な個人情報（個人情報保護法） |
| 標準料理マスタ／食材マスタ | 料理ごとの区分・材料・アレルゲンなどの基本データ／食材ごとの単位・パックの量・売り場などの基本データ |
