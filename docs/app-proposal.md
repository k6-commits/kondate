# 企画提案：LLMを活用した献立アプリ

- 作成日：2026年11月8日
- 前提資料：[research-report.md](research-report.md)（市場調査レポート）

---

## 1. 結論：何を作るか

**仮称「きめとく」― うちの献立当番**

> 献立を「作る」AIではなく、「回す」AI。
> 家族がふだん食べている定番料理を覚えて、買い物日に合わせて平日の夕食と正確な買い物リストを先に決めておく。何もしなければそのまま確定し、予定が崩れたら1タップで組み直す。

- **対象**：日本の共働き・子育て世帯で、平日の夕食を主に決めている人とそのパートナー
- **入口**：LINE公式アカウント（友だち追加だけで始められ、パートナーも同じ献立と買い物リストを見られる）
- **約束**：「今日なに作ろう」を考える回数を、週5回から週1回以下に減らす

**LLMの使い方**

- LLMは裏方に徹する。担当は次の3つ。
  - 話し言葉や写真を、アプリが扱えるデータに直す
  - 検証済みの候補の中から、その家庭に合う献立を選ぶ
  - 理由を一言で添える
- アレルゲン・分量・買い物リストの正しさは、コードで保証する。

## 2. なぜこのアプリか（調査からの根拠）

| 調査でわかったこと | だからこうする |
|---|---|
| 負担の中心は「作る」より「決める」こと。共働き家庭の87.0%が「献立を考える」を負担に挙げ、その割合は増え続けている（[2-1](research-report.md#2-1-つらいのは決めること)） | レシピを探す道具ではなく、決める役を引き受ける道具にする。成功指標も「閲覧数」ではなく「考えずに済んだ夕食の数」にする |
| 「アプリが失敗するのは、脳がしたくない毎日の決定を増やすから」（r/ADHD）。選択肢が多いと、かえって固まる | 毎日2〜3案から選ばせない。1案を既定にして、何もしなければ確定。触るのは例外のときだけ |
| 多くの家庭は限られた定番を回している（米国の専門家の見立てでは10〜15品）。新しいレシピより、いつもの料理を回したい | 「うちの定番帳」を中心に組み、新しい料理は週1〜2品だけ混ぜる |
| ChatGPTに丸投げすると特売や在庫と合わない（「いや、それ買いに行かないやん」）。固定の計画は生活とずれてすぐ破綻する | 家庭の状態（定番・買った物・作った物・家族の反応）を持ち続け、崩れたら毎日組み直す |
| 惣菜・冷凍食品に罪悪感がある人は72.9%いるが、手間を減らすことへの支持は81.5% | 冷凍食品・惣菜の「ラク日」を、最初から正規の献立として組み込む |
| 献立を考えるのは妻97.7%、夫36.7%。アプリが「女性の管理対象を一つ増やすだけ」になる懸念 | LINEの家族グループで夫婦が同じ献立とリストを持ち、差し替えや買い物を分担できるようにする |
| LLMの献立は、アレルゲンの混入（56件中4件）や分量のずれを起こす。ただし、データベースとルールで縛れば精度は大きく上がる | 献立の正しさはコードで保証し、LLMには検証済みの候補からしか選ばせない |
| 不満の筆頭は課金のしかた（低評価の36%）。海外では単体のAI献立アプリが相次いで終了した（Mealime、Ollie） | 中核の機能は無料にし、強制トライアルをしない。資金調達に頼らない小さな規模で黒字化を目指す |
| 献立から買い物カートまでの機能は、海外では小売や汎用AIの標準になった。単に「献立を生成する」だけでは差がつかない | 生成ではなく運用で勝負する。強みは、家庭ごとに貯まるデータと信頼 |

## 3. 誰のためのアプリか

**主なターゲット**

- 首都圏など都市部の、共働き・子育て世帯（子どもは未就学〜小学生）
- 平日の夕食の献立を主に決めている人（多くは母親）と、買い物や調理を分担するパートナー
- 週に数回は自炊していて、作れる定番はある。けれど毎日決めるのがつらい

**このターゲットを選ぶ理由**

1. 「献立を決める負担」を示すデータが最も厚い層だから。
2. 日本の献立の形（主菜・副菜・汁物、旬、弁当、まとめ買い、冷凍）に合わせて作り込むことが、海外勢や汎用AIに対する差になるから。
3. 家族で使うため、1回の獲得で2人が利用者になり、乗り換えには夫婦の合意が要る。この点が防御になるから。

**後から広げる層**

- 単身・学生（少量・節約）
- 高齢の親がいる世帯（減塩、やわらかさ）
- アレルギーのある家庭（取り分け）
- 健康目標がある人（たんぱく質など）

いずれも、中核の仕組み（定番帳・エンジン・検証層）が育ってから広げる。

## 4. どんな体験か（ある家庭の1週間）

**日曜の夜（買い物日の前夜）**　LINEの「献立」グループに届く

```
きめとく：今週の夕食です。何もしなければこのまま確定します。
  月 鶏の照り焼き／小松菜のおひたし／豆腐とわかめの味噌汁（25分）
  火 豚こまと白菜の味噌炒め／卵スープ（20分）
  水 ラク日：冷凍ぎょうざ／もやしナムル（10分）
  木 鮭のホイル焼き／ポテトサラダ（多めに作って金曜のお弁当に）
  金 カレー（甘口を先に取り分け）／サラダ（35分）
  [買い物リストを開く]  [差し替えたい日を選ぶ]
```

- **買い物リスト**：売り場順に並び、人数分に換算され、パック単位に丸めてある。夫婦どちらのスマホからでもチェックでき、チェックした物は「家にある物」として記録される。
- **差し替え**：その日について、別の案を2つだけ示す。

**月曜の朝（有料）**

```
きめとく：今夜は鶏の照り焼き。鶏ももを冷凍室から冷蔵室へ移しておいてください。
```

**火曜の夕方**　メニューの「今日のごはん」をタップする

```
きめとく：今日は豚こまと白菜の味噌炒め（20分）。白菜を使い切るなら今日がおすすめです。
  [作った]  [別のに]  [今日は無理]
→ [今日は無理]
きめとく：了解です。今日はラク日にして、冷凍うどんと卵でどうでしょう。
         豚こまと白菜は明日に回します（豚こまは明日使えなければ今夜冷凍を）。
  [OK]  [ほかの案]
```

**食後**

- 家族の反応を◎○△で1タップ記録する（子どもの分は親が代わりに入力してもよい）。
- ◎の料理は出番が増え、△の料理はしばらく出ない。
- 子どもは翌週の候補に2択で投票できる。

**金曜の夜**

```
きめとく：今週は5日のうち4日、考えずに済みました。
         いちばん人気は鶏の照り焼き（◎3人）。使い切った食材：白菜、小松菜、鮭。
```

**ポイント**

- ユーザーが自分から何かをするのは、「差し替え」「今日は無理」「反応」の3つの例外だけ。
- チャットは使わなくてもよい。「水曜は夫が飲み会」「卵切れた」のように書けば、LLMが人数や在庫の変更として受け取る。

## 5. 機能

### 5-1. MVP（最初の3か月で作るもの）

| # | 機能 | 中身 |
|---|---|---|
| 1 | **1分で始める** | 質問は3つだけ：家族の人数と年齢帯、除外食材・アレルギー、買い物の曜日。よく作る料理を10品ほど、話すか打つかで入力すると、LLMが標準料理マスタと照合して「うちの定番帳」を作る。ユーザーは確認するだけ。買い物日を待たずに、今週の残りの日の献立を出す |
| 2 | **うちの定番帳** | 名前だけの得意料理、他サイトやSNSのレシピのリンク、冷凍食品、惣菜を同じ扱いで登録できる。定番ごとに「うちの材料メモ」（豚か牛か、など）を持てる |
| 3 | **週の献立エンジン** | 買い物日を起点に、平日の夕食5日分を組む。満たす条件：主菜＋副菜または汁物、週内の偏り（和洋中・肉魚）、旬、除外条件、新しい料理は週1〜2品、ラク日は週1日。何もしなければ確定し、差し替えは2択 |
| 4 | **正確な買い物リスト** | 人数換算、単位の統一（個とg）、同じ食材の集約、パック単位への丸め、常備調味料の除外を、すべてコードで計算する。売り場順に並べ、夫婦で同期する |
| 5 | **今日のごはん／今日は無理** | 当日の献立をボタン1つで返し、「作った／別のに／今日は無理」を1タップで記録する。「今日は無理」のときは冷凍・惣菜・5分メニューに差し替え、使わなかった生鮮を傷みやすい順に翌日以降へ回す。**この機能は無料で、回数制限もない** |
| 6 | **家族の反応と振り返り** | ◎○△の記録、子どもの2択投票、週末の「考えずに済んだ夕食の数」「使い切った食材」の表示 |
| 7 | **外部レシピのリンク登録** | URL、SNSの投稿、写真から、料理名と材料の候補をLLMが取り出す。本文・手順・写真は保存せず、作り方は元のページへ案内する。「このレシピ、うちの除外食材は入っていない？」の確認にも使える |
| 8 | **信頼の土台** | 除外食材・アレルゲンを辞書とルールで判定し、わからない物は「要確認」と表示する。データはいつでも書き出せる |

**MVPで作らないもの**：ネイティブアプリ、写真からの在庫登録、特売データ連携、栄養の数値表示、ネットスーパーとの連携

### 5-2. 第2段階（4週間の継続率を確かめた後）

- **レシートや注文画面の取り込み**：レシート、生協・ネットスーパーの注文画面のスクリーンショットから、買い物リストを自動で消し込み、在庫を補正する。合計額で照合し、自信のない行だけ確認してもらう。画像は読み取ったら削除する。
- **1食あたりの実際の食費と使い切りの週報**：物価高の中で、節約の実感が続ける理由になる。
- **弁当・子どもの昼食・夏休みなど長期休暇のモード**：夕食を多めに作って翌日に回す。「今日のお昼ごはん何？」が負担という母親は65.4%。
- **予算と特売のモード**：地域スーパーや生協と組む。
- **複数の買い物日**：週1回のまとめ買いと、生協の宅配の併用など。

### 5-3. 第3段階

- **共通のベース料理と取り分け・後のせ**：カレーは甘口を先に取り分ける、麻婆豆腐は豆板醤を入れる前に分ける、など。子ども・高齢の親・減量中の人に対応する。
- **アレルギーのある家庭向けのモード**：法務設計と管理栄養士の監修をそろえてから出す。
- **減塩・たんぱく質の目安表示**：日本食品標準成分表で計算し、管理栄養士が監修する。
- **汎用AIとの接続**：ChatGPT、Claude、Geminiから「我が家の献立台帳」を参照・更新できるコネクタ（MCP）を作る。入口を汎用AIに取られても、データの持ち主であり続けられる。
- **企業向けの提供**：生協・地域スーパー・食品メーカーにエンジンを提供する。

## 6. 既存アプリ・汎用AIとの違い

| | 大手レシピアプリ（クックパッド、クラシル、デリッシュキッチン） | me:new など自動献立 | 汎用AI（ChatGPT、Gemini、LINE「Agent i」） | 海外の小売AI（Instacart など） | **きめとく** |
|---|---|---|---|---|---|
| 中心にあるもの | 自社レシピの検索・保存 | 自社レシピからの自動献立 | その場の相談とレシピ生成 | 自社の店での購入 | **家庭の定番と状態** |
| 決める回数 | 多い（自分で選ぶ） | 少ない | 毎回頼む必要がある | 少ない | **最小（既定で確定）** |
| 崩れたとき | 自分で探し直す | 作り直し | 毎回説明し直す | — | **1タップで組み直す** |
| 買い物リストの正確さ | 良い | 分量のずれへの不満 | 不安定 | 良い | **コードで保証** |
| アレルゲン | 自分で確認 | 除外できる | 数%で漏れる（研究） | — | **ルール判定＋「要確認」** |
| 家族 | 個人単位 | 家族グループ | 個人単位 | 世帯 | **夫婦で分担・子どもも投票** |
| 中立性 | 自社レシピが前提 | 自社レシピが前提 | — | 自社の店が前提 | **他社レシピ・冷凍・惣菜も同じ扱い** |

**防御の考え方**：機能そのものは真似される前提で考える。真似しにくいのは次の4点。

1. **世帯ごとに貯まるデータ**：定番帳、家族の◎○△、調理の記録、推定在庫。使うほど当たるようになり、夫婦で使えば乗り換えには2人の合意が要る。
2. **中立性**：他社のレシピや冷凍食品・惣菜を同じ扱いにし、広告を出さず、「買いすぎない」を目標にする。自社レシピの閲覧・広告・購買データで稼ぐ大手には取りにくい立ち位置である。
3. **信頼**：除外の違反ゼロ、正確な買い物リスト、誠実な課金、データの持ち出しの保証。
4. **小さく黒字にする**：レシピ制作や広告営業を持たない。資金調達に頼らない規模で回し、大手が本気で取りに来る前に定着させる。

## 7. LLMの使いどころと技術構成

### 7-1. LLMに任せること・任せないこと

| 処理 | 担当 | 理由 |
|---|---|---|
| 話し言葉・音声の料理名を、標準料理マスタと照合する | LLM（確定は人） | 表記ゆれ（「ばあばの煮物」「うちの豚汁」）を吸収できる |
| 家族の書き込みを、変更の指示に直す（「水曜は夫いらない」→人数、「卵切れた」→在庫） | LLM | 入力の手間を減らす中心機能。あいまいなときは聞き返す |
| 週の組み合わせを選ぶ | **エンジンが候補を作り、LLMはその中から選ぶ** | 候補にない料理は出せない構造にして、条件違反を仕組みで防ぐ |
| 理由の一言（「月曜に買ったキャベツを使い切るため」） | LLM（事実はコードで照合） | 食材名や日付が実データにない文は、定型文に差し替える |
| 外部レシピから料理名・材料を取り出す（URL・SNS・写真） | LLM（確定は人） | 画像や動画の説明文を読むのはLLMの得意分野 |
| アレルゲン・除外食材の判定 | **コード（辞書とルール）** | 違反はゼロでなければならない。わからない物は「要確認」で止める |
| 分量・単位換算・買い物リストの集約・在庫の差し引き | **コード** | LLMに数値を作らせない |
| レシピの手順や分量 | **書かせない** | 定番は家族が作れる。新しい料理は元のページへ案内する |
| 栄養の数値 | **MVPでは出さない**（後に成分表で計算） | 研究では、LLMの栄養推定は大きくずれる |

### 7-2. 構成

```
LINE公式アカウント（Messaging API）＋ LIFF（LINE内で開くWeb画面）
        │   ※画面はWebで作り、後でPWAやネイティブアプリに移せるようにする
        ▼
API サーバー ── データベース（世帯、メンバーの年齢帯と除外、定番帳、
        │                       標準料理マスタ約300品、計画、買い物リスト、
        │                       推定在庫（たっぷり／少し／なし）、反応）
        ├── 献立エンジン（条件を満たす候補の生成。ソルバ）
        ├── 検証層（除外・旬・多様性・分量。生成の前後で全件チェック）
        └── LLM 層
              ・構造化出力（JSONスキーマ）で結果を受け取る
              ・選べるのは候補IDのリストだけ
              ・失敗したら再試行し、それでも駄目ならエンジンだけで提案する
              ・家族の名前や子どもの情報は送らない（IDに置き換える）
```

- **夜間に週の計画をまとめて作る**：買い物日の前夜にまとめて計算しておけば、応答は数秒以内で済む（海外では「生成に5分かかる」ことへの不満があった）。
- **評価セット**：家族構成・除外・買い物日・崩れ方の組み合わせを数百ケース用意し、モデルやプロンプトを変えるたびに回帰テストする。
  - 「全特定原材料×全料理」の除外判定テストも含める。
  - 最新の汎用LLMが同じテストでどれだけ違反するかも定期的に測り、差別化の根拠として公開する。
- **データ**
  - 栄養計算には、文部科学省「日本食品標準成分表（八訂）増補2023年」を使う（第3段階）。
  - アレルゲンは、消費者庁の特定原材料等の最新リストに合わせて更新する。

### 7-3. モデルと費用の目安

Claudeを使う場合の例（2026年10月時点の公開価格。実装時に公式ページで確認すること。他社のモデルでも構成は同じ）。

| モデル | ID | 入力／出力（100万トークンあたり） |
|---|---|---|
| Claude Opus 5.5 | `claude-opus-5-5` | $4／$20 |
| Claude Sonnet 5.5 | `claude-sonnet-5-5` | $2／$10 |
| Claude Haiku 5.5 | `claude-haiku-5-5` | $0.10／$0.50 |

この設計では、LLMの担当は構造化・候補からの選択・短い文に限られる。そのため、費用はどのモデルを使うかでほぼ決まる。

**1世帯・1か月あたりの概算**

- 前提：週の計画4回、書き込みの解釈30回、リンクの取り込み5回。思考に使うトークンも含め、1ドル＝150円で計算した。

| 使うモデル | 1世帯・1か月あたり |
|---|---|
| すべて Opus 5.5 | 約1.2ドル（約180円） |
| すべて Sonnet 5.5 | 約0.6ドル（約90円） |
| すべて Haiku 5.5 | 約0.03ドル（約5円） |

**収入との比較**

- 有料会員からの収入は、月約320円（年3,800円÷12）。
- 無料の利用者も含めて均すと、1世帯あたり月10円程度にしかならない（ダウンロードから有料への転換率を2.9%とした場合）。
- つまり、最上位モデルだけで全員を処理する設計は成り立たない。

**進め方**

1. まず最上位のモデルで品質の基準を作る。
2. 評価セットで品質が落ちないと確かめた処理から、軽いモデルに移す（料理名の照合や書き込みの解釈は、軽いモデルで足りる見込み）。
3. 無料版の週の計画は、エンジンだけでも回るようにする。LLMは理由の一言などに限る。
4. 週の計画は、夜間のバッチ処理（単価が半分）とプロンプトキャッシュを使って安くする。

## 8. 信頼と安全のルール

| 領域 | ルール |
|---|---|
| **アレルギー・除外** | 判定はコードで行い、違反ゼロをリリース条件とKPIにする。市販のルウ・調味料・冷凍食品は銘柄で原材料が違うので「要確認」とし、パッケージの表示を確認するよう促す。アプリは除外の補助であって、保証ではないと明示する。MVPでは、重いアレルギーの管理と医療的な食事療法（糖尿病・腎臓病など）を対象外にする |
| **乳幼児** | 1歳未満の家族がいる場合、はちみつを含む料理はその子の分から外す（乳児ボツリヌス症）。離乳食はMVPの対象外 |
| **食中毒** | 生鮮の使用期限はLLMに推測させない。保守的な固定日数で早めの日に割り当て、「においや色を確認して」と添える。作り置きは保存日数を表示する |
| **危険な入力** | 食品でない材料や、危険な組み合わせを求める入力は、入力の段階で止める（Pak'nSaveの事例） |
| **レシピの権利** | 外部レシピの本文・手順・写真は保存しない。料理名、自分用の材料メモ、出典リンクだけを持ち、元のページへ送客する。MVP前に料理家に画面を見せて意見を聞く |
| **個人情報** | アレルギーなど健康に関わる情報は、要配慮個人情報に当たり得るものとして、取得時に明示的な同意を得る。子どもの情報は年齢帯とニックネームだけにする。LLMには名前を送らない。LINEのボットは献立専用のグループにだけ入り、呼びかけ以外の発言は保存もLLMへの送信もしない |
| **課金** | 価格を最初に示す。強制トライアルもカードの先行登録もなし。更新前に通知し、すぐ解約できる。データはいつでもCSV／JSONで書き出せる。サービスを終了するときは移行期間を設けると規約に書く |
| **AIの表示** | AIが選んだことと、その理由を一言で示す。AIの機能を使わなくても（エンジンだけで）献立が回るようにする |

## 9. ビジネスモデル

### 9-1. 無料と有料の線引き

| | 無料 | 有料「当番プラン」 |
|---|---|---|
| 週の献立と買い物リスト | ○ | ○ |
| 夫婦2人での共有、除外食材の指定 | ○ | ○ |
| 今日のごはん／今日は無理（その場の組み直し） | ○（回数制限なし） | ○ |
| 定番帳・リンク登録 | 30品まで | 無制限 |
| 毎日の自動通知（朝の「解凍して」と夕方の「今日はこれ」） | — （メニューから自分で開く） | ○ |
| 家族一人ひとりの好みの学習、3人目以降の参加 | — | ○ |
| 複数の買い物日 | — | ○ |
| 弁当・昼食・長期休暇のモード、レシート取り込み、予算・特売（第2段階） | — | ○ |

**線引きの考え方**

- 決める負担の中心（週の献立から買い物リストまで）と、困った瞬間の「今日は無理」は無料にする。
- 有料にするのは、「使える範囲を広げるもの」と「配信の費用がかかるもの」である。

**価格**

- 月480円、年3,800円。年額を主に勧める（1年後の継続率は、年額44.1%、月額17.0%）。
- カード登録不要の2週間全機能トライアルを用意する。

### 9-2. 収支の見立て

- **LINEの配信費**
  - 通数は「送信回数×受け取る人数」で数える。ユーザーのメッセージへの応答は通数に含まれない（[LINE Developers、2026年5月](https://developers.line.biz/ja/tips/2026/05/28/how-to-count-messages/)）。
  - 料金プランに含まれる無料通数を超えると、1通数円かかる。追加メッセージの料金は2026年10月に改定されたとの情報があるため、実装時に公式ページで確認する。
  - 夫婦2人に毎日配信すると月60通前後になり、1通3円なら1世帯あたり月約180円かかる。
  - このため、無料版は応答を中心にし、配信は週1回にとどめる。毎日の配信は有料会員だけにする。
- **費用の条件**：無料利用者1世帯あたりの費用（LINE＋LLM）を月数円に抑えることが、事業が成り立つ条件になる。β版ではこれをKPIとして測る。
- **決済手数料**：LINEとWebで提供する間は、Web決済を使えばアプリストアの手数料（15〜30%）がかからず、数%の決済手数料で済む。
- **1世帯から得られる収益（LTV）**
  - 年3,800円で1年後の継続率44.1%なら、有料1世帯のLTVは約5,800〜6,800円（ストア手数料の有無による）。
  - ダウンロードから有料への転換率を2.9%（ヘルス・フィットネスの中央値）とすると、1ダウンロードあたり約170〜200円しかない。広告で獲得しても回収できない。
- **獲得の経路**：次の4つを中心にする。
  - 夫婦の招待
  - 保育園・学童の保護者コミュニティ
  - 「名もなき家事」をテーマにしたPR
  - 無料の「このレシピ、うちは大丈夫？」チェック
- **目標規模**：有料1万世帯で年約3,800万円。2〜3人のチームが資金調達なしで黒字になる規模である。クックパッドの有料会員（130.7万人）の1%未満で、大手が本気で取りに来にくい。
- **第2の柱（第3段階）**：生協・地域スーパー・食品メーカーへのエンジン提供と送客。
  - 生協の週1回の宅配は、買い物日を起点にした週計画と同じリズムで動く。
  - ただし特定の1社に依存しない（未来献立の終了や、Mealimeの閉鎖の教訓）。

## 11. リスクと対策

| リスク | 対策 |
|---|---|
| **大手やLINEヤフーが同じ機能を出す**（Agent iにはレシピ機能があり、デリッシュキッチンは余り食材の指定と1週間の計画をすでに持っている） | 機能ではなく、蓄積・中立性・信頼で勝負する。中核のデータとロジックは自社側に置き、LINEは入口の一つにとどめる。小さく黒字化して、蓄積を先に進める |
| **「ChatGPTなら無料」と比べられる** | 検証で汎用AIと並べて比べ、買い物リストの誤り・在庫とのずれ・作り直しの回数を数字で示す |
| **課金の実績が日本では弱い**（献立AI単体はほぼ育っていない。未来献立は終了、クックパッドは有料会員が減少） | コードを書く前に、年額の前払いで支払い意思を確かめる。届かなければ、生協・小売向けの提供に軸を移す |
| **最初の入力が面倒で離脱する** | 3問と料理名10個で、1分以内に初回の献立を出す。在庫は手入力させない |
| **推定在庫がずれる** | 完璧な在庫管理は目指さない。在庫は3段階で持つ。無反応を「作った」とはみなさず、提案のときに「鶏むね、まだある？」と1問だけ確かめる |
| **アレルギーの事故** | コードでの判定、「要確認」、回帰テスト、対象外の明示（8章）。重いアレルギー向けのモードは、法務と監修をそろえてから |
| **料理家の反発** | 本文を保存せず、元のページへ送客する。将来は「作られた回数」のレポートや収益分配で味方にする |
| **LINEへの依存**（仕様・料金の変更） | 画面はWebで作り、PWAやネイティブアプリに移せるようにする |

## 13. 検討した別案

この提案は、1案だけ考えて決めたものではない。調査メモだけを渡した4人の企画担当（AIエージェント）に、それぞれ別の視点から独立に案を作らせた。私自身の最初の案も加えた5案を、3人の審査役（利用者・事業戦略・開発と安全の視点）が6項目で採点した（各項目10点満点で60点満点、3人の平均）。

| 案 | 視点 | 中身 | 平均点 | 評価 |
|---|---|---|---|---|
| **B「うちの献立当番」** | 事業の防御力 | 中立な定番帳、決定論的なエンジン、世帯単位のサブスク、前払いでの検証 | **38.3** | 事業設計が最も堅い。ただし入口がネイティブアプリで、獲得と夫婦共有に壁がある。無料版で「今日は無理」が使えない点も問題とされた |
| **D「台所番」** | 技術 | レシートを撮るだけで家の食材が台帳になり、傷みそうな物から使い切る献立を出す | 35.7 | LLMの活用度は最大。しかし毎回のレシート撮影が前提で、台帳がずれやすい |
| **A「きめとく」** | ユーザーの痛み | LINEで週の献立が届き、何もしなければ確定。ラク日、子どもの投票 | 35.0 | 体験は最も良い。ただし無料版で毎日LINEに配信するため、利用者が増えるほど赤字になる |
| **C「おなじごはん」** | 取りこぼされた層 | 食物アレルギーの子がいても家族全員が同じ夕食を食べられる献立。共通ベースと取り分け | 31.3 | 差別化は強い。しかし見落とし1件で事業が終わる責任の重さと、市場の小ささが問題 |
| E「こんだて番」（私の最初の案） | — | 定番・在庫・特売・予定から毎日の献立を決める | 27.0 | 「突破口がない」「献立の組み合わせをLLMに任せている」「家族共有を有料にしている」と指摘された |

**審査役3人の結論は一致した。**

- 土台にはAとBを統合する。体験と入口はAから、課金・防御・検証の設計はBから取る。
- Cの「取り分け」と「要確認」、Dの失敗時の設計を移植する。
- Dのレシート取り込みは、継続率を確かめた後に足す。

この提案書はその統合案である。私の最初の案への指摘（LLMに組み合わせを任せない、共有を有料にしない、狙いを絞る）も反映した。

**別の方向として検討したもの**

- **SNSのレシピ保存アプリ**（海外のReciMe型）：課金の実績はあるが、日本ではクックパッドが同じ機能を出して炎上した。この提案では、単独のアプリではなく「定番帳への入口」として取り込む。
- **単身・学生向けの節約自炊アプリ**：ニーズはあるが支払い能力が低く、家族ほど防御も効かない。中核が育った後に、少量・節約のモードとして広げる。
- **写真でカロリーを計算するアプリ**（Cal AI型）：急成長した領域だが、献立とは別の市場で、競争も激しい。
