# きめとく（仮）プロトタイプ 設計書

企画は [../docs/app-proposal.md](../docs/app-proposal.md)。このプロトタイプは、提案の中核の体験を触って確かめるためのもの。

## 1. 目的と範囲

**確かめたい体験**

1. 3つの質問と定番料理で、すぐに今週の献立が出る
2. 何もしなければ確定。差し替えは2択だけ
3. 正確な買い物リスト（売り場順、パック単位、買い物日ごと）
4. 「今日は無理」で1タップ組み直し
5. 「@きめとく 鶏むねが安い」などの書き込みで献立が変わる
6. 家族の反応（◎○△）で、次の週の提案が変わる
7. 除外食材とアレルゲンの判定、「要確認」、注意書き

**実装の方針**

- **LLMなしで全部動く。** 献立はエンジン（ルールと点数）で作り、書き込みはルールベースで解釈する。
- **サーバーに `ANTHROPIC_API_KEY` があるときだけ、書き込みの解釈にLLMを使う**（失敗したらルールベースに戻る）。
- **UI はブラウザだけで動く**（状態は localStorage）。日付は「翌日へ進む」で動かし、1週間の流れを体験できる。本物の家族での1週間の試用では、日付を本物の日付（日本時間）に合わせて進め、週末の質問と試用の記録で数を集める（3-11・3-12・4章・7章）。
- **LINE とのつなぎ込み**は server/ に置く（webhook の受信と返信）。動かすには、LINE の Messaging API のチャネルが要る。

**作らないもの**：本物の課金、ネイティブアプリ、写真からの在庫登録、特売データ連携、栄養の数値。

## 2. 構成と担当

```

  src/engine/   献立エンジン（純粋なTS。DOM も Node API も使わない）
    types.ts    すべての型（契約）

    dates.ts / rng.ts
    （実装：planner.ts, safety.ts, shopping.ts, replan.ts, parser.ts, conversation.ts, state.ts など。
      1週間の試用：checkin.ts（週末の質問）, trial.ts（試用の記録））
  src/data/     料理マスタ・食材マスタ・アレルゲン
  src/ui/       React の画面（スマホ幅で作る）
  src/report/   1週間の試用の集計ページ（report.html。主催者用。7章）
  server/       Hono のサーバー（LINE webhook、LLM での解釈、JSON ファイルの保存）
```

- テストは Vitest。エンジンのテストは、マスタに頼らない小さなフィクスチャで書く（マスタの検査は src/data のテスト）。
- `npm run typecheck`、`npm test`、`npm run build` が通ること。

## 3. エンジンのルール

### 3-1. 献立を作るタイミング

- **初回**：今日を含む今週の献立日（既定は月〜金）のうち、今日以降の分を作る。買い物リストも作る。
  - **土曜・日曜に始めたとき**（今週の献立日が残っていない）：すぐに来週の献立を作る（「すぐに献立が出る」ため）。
  - 来週の作る日（下）をもう過ぎていたら（例：水曜に始め、買い物も水曜）、今週と来週の両方を作り、両方の週の献立を知らせる。
- **週の献立を作る日**：その週の最初の献立日の材料を買う日（その日以前で最も近い買い物日）の前日。
  - 例：買い物日が日・水なら、土曜に来週（月〜金）の献立を作る。献立が水〜金で買い物が水なら、その週の火曜に作る。
  - 献立日の前に買い物日がない場合は、今日を買い物日として扱う。
  - 「翌日へ進む」で、来週分が作る日を過ぎていて、まだなければ作る。今週分がまだなく（献立日が週の後半だけの設定、読み込んだ状態 など）、今週の作る日を過ぎていれば、今週分も作る。
- 有料版では、週の献立を作ったときに配信メッセージ（push: true）で届ける（今週分・来週分のどちらでも）。無料版では配信しない。
- **確定**：何もしなければそのまま確定（状態は planned のまま）。

### 3-2. 1食の組み方

- **通常の日**：主菜1品＋副菜または汁物1品（`sidePolicy` が 'side_or_soup' の場合）。
- **ラク日**（`rakuPerWeek`、既定1日）：role が 'raku' の料理（冷凍ぎょうざ、惣菜、冷凍うどん など）＋必要なら副菜を1品。
  - ラク日は、週の中ほど（水曜など）か、調理時間の上限が短い曜日を優先する。
  - 理由には「主食・主菜・副菜」がそろうかどうかではなく、罪悪感を減らす一言を添える（例：「今日はラクする日。冷凍ぎょうざで十分」）。
  - ラク日の副菜は、10分以内で、買ってから冷凍・解凍しなくてよい物だけ。合う物がなければ付けない。
- 料理のタグで、足す物を変える：`complete`（それだけで1食。例：納豆ごはんと味噌汁）には何も足さない。`soupy`（汁気が多い。汁のある麺・シチュー・ポトフ・鍋）には汁物を足さない（副菜は足してよい）。

### 3-3. 点数のつけ方（主菜の選び方）

候補ごとに点数をつけ、点数の高いものから日に割り当てる（seed つきの乱数で同点を崩す）。

| 要素 | 点数の目安 |
|---|---|
| 定番帳にある | +3 |
| 家族の反応：◎ / ○ / △ | +2 / +0.5 / −4（直近の反応ほど重く） |
| 7日以内に食べた | −6（14日以内は −2） |
| 前日と同じたんぱく源 | −3 |
| 前日と同じジャンル（和洋中） | −1 |
| 旬の食材を使う | +1 |
| 在庫で傷みやすい食材を使い切れる | +2 |
| その曜日の調理時間の上限を超える | −5 |
| 子どもがいて kidFriendly | +0.5（spicy なら −2） |
| 買い物日から離れすぎて、傷みやすい食材が持たない | −4（冷凍できるなら −1 にして「買ったら冷凍」のメモ） |

- **新しい料理**（定番帳になく、履歴もない料理）は、週に `newPerWeek` 品（既定1）だけ入れる。
  - アプリは作り方の本文を持たない。まだ作っていない新しい料理の日は、カード（画面のカードと、LINE で送るカードの文）に「作り方：「〇〇」ははじめての料理です。作り方は、料理名でレシピを探してください。」を添える（特定のサービスには寄せない）。
- **魚**は、週に1回は入れたい（候補があれば）。買い物日の当日か翌日に置く。
- 副菜・汁物は、主菜とジャンルが合うもの、主菜と同じ食材を使い回せるもの、在庫を使い切れるものを優先する。
  - 使い回しは、片方では少量（付け合わせのキャベツ、パックの残り）のときだけ加点する。主菜の主な材料（1人あたり g・ml は70以上、個は0.5以上 など。料理名に出ている食材も含む）を、副菜・汁物の主な材料（g・ml は40以上 など）にもう一度使う組み合わせは減点する（例：肉じゃが＋じゃがいもと玉ねぎの味噌汁、かに玉＋中華風たまごスープ）。
  - 主菜と同じたんぱく源の副菜・汁物（豚の主菜に豚汁、卵の主菜にたまごスープ）は、使い回しとジャンルの加点より強く減点する（−6）。
- **理由（reasons）**は、点数の要素からテンプレートで作る（例：「家族に人気（◎2）」「白菜を使い切るため」「前日が肉なので魚に」「旬のさんま」）。1食あたり1〜2個。
  - 優先する順：使い切り ＞ 家族に人気 ＞ 前日が肉なので魚に・新しい料理 ＞ うちの定番 ＞ 旬 ＞ 使い回し。
  - 旬・使い切り・使い回しの理由は、1人あたりの量がある程度ある食材（g・ml は20以上 など）からだけ作る（1人3gの薬味は理由にしない）。使い回しは、相手が汁物なら「汁物でも」と書く。

### 3-4. 安全（safety.ts）

- 判定の対象は、その日に食べるメンバー（乳児を除く）の除外条件。
  - **allergen**：食材の allergens（派生原材料を含む）に含まれていれば excluded。
  - **ingredient**：その食材の id が含まれていれば excluded。
  - **text**：語を区切り（、・,／ かっこ 空白）、それぞれの語で判定する（「ピーマン、しいたけ」は両方）。語の「アレルギー」「が苦手」「嫌い」「類」「全般」「製品」は外して照合する。
    - 食材の名前・別名、または料理名にその語が含まれていれば excluded。食材の総称（`genericAliases`。「鶏肉」「きのこ」）は使わない。
    - **分類の語**は、その種類の食材にも当てる：魚（kind が fish。ちくわ・かまぼこ・かつお節も）、魚介（fish と seafood。貝・オイスターソースも）、貝（あさり・オイスターソースなど）、肉（鶏・豚・牛・ひき肉とベーコン・ハム・ウインナー・ガラスープ・コンソメ）、ひき肉、きのこ、海藻。
    - **アレルゲンとしての扱い**：語がアレルゲンの名前なら、アレルゲンの除外としても判定する（派生原材料・要確認も含む）。ひらがな・カタカナ・漢字（えび・エビ・海老）、「卵白」「卵黄」「とり肉」「チキン」「ぶた肉」「ポーク」「ぎゅう肉」「ビーフ」、「〇〇アレルギー」「〇〇のアレルギー」「〇〇類」「〇〇類アレルギー」の形を受け付ける。語尾は「アレルギー」→「類・製品」の順に外しながら引く（「甲殻類アレルギー」→「甲殻類」）。
    - まとめた呼び方：甲殻類（えび・かに）、ナッツ・木の実、魚卵（いくら）、肉（鶏肉・豚肉・牛肉）、魚（さけ・さば・いくら）、魚介・海鮮（魚と、えび・かに・いか・あわび）、貝（あわび）。部分一致はしない（「鶏もも」「ひき肉」はアレルゲンにしない）。
  - 画面で自由入力の除外を登録するときは、`textExclusionTargets` で「当たるアレルゲン・食材・料理」と「どれにも当たらない語」を見せる（当たらなければ「当たる食材はありません」）。入力がアレルゲンの語（`allergensOfText` が空でない。「鶏肉」「甲殻類」）なら、アレルゲンとしての除外（加工品・調味料の分も除く）を候補の先頭に出す。
- 食材が `uncertain`（銘柄で原材料が変わる加工品）で、世帯に allergen の除外があれば、その料理は 'uncertain'（要確認）。
- 材料がわからない自由入力の定番は、料理名から分かる範囲で判定する（アレルゲンの呼び方。「鮭」「豚」「蟹」のような漢字1文字も使う。分類の語は、その種類の食材の名前）。当たらず、世帯に allergen の除外があれば 'uncertain'。
- **献立に出すのは 'ok' だけ。** 'uncertain' は `allowUncertainWithExclusions` が true のときだけ出し、warnings に「要確認：〇〇は銘柄で原材料が違います。パッケージの表示を確かめてください」を入れる。
- **householdNotices**
  - 常に：「アプリは除外の補助で、アレルギーの安全を保証するものではありません」
  - severe の除外がある：「重い食物アレルギー（アナフィラキシーの経験など）は、このプロトタイプの対象外です。医師の指示を優先してください」
  - 乳児がいる：「1歳未満の子は献立の『食べる人』に含めていません（離乳食は対象外）」「1歳未満の子には、はちみつ（はちみつ入りの加工品を含む）を与えないでください」
  - 幼児・乳児がいる：「5歳以下の子には、豆・ナッツ類など、のどに詰まりやすい食品に注意してください」
- 食中毒の注意：「消費期限を優先してください。においや色では安全を判断できません」（冷凍のメモや期限が近い食材を回すときに添える）。

### 3-5. 人数と分量

- `servings` = その日に食べるメンバーの SERVING_WEIGHT の合計（欠席者と乳児を除く）。
- 必要量 = Σ（料理の材料 amount × servings）。定番に `overrides` があればそちらを使う。
- 表示は、食べる人数（乳児と欠席の人を除く）を主にし、小学生・幼児がいて大人換算と違うときだけ換算を添える：カードは「4人分（大人換算3.2）」、返事の文のかっこの中は「（3人分、大人換算2.2）」、大人だけなら「2人分」。画面とカードの文（LINE）で同じ表現にする。小学生・幼児のいる家族には、画面に換算の説明（大人・中高生を1人分、小学生を0.7人分、幼児を0.5人分）を1行出す。

### 3-6. 買い物リスト（shopping.ts）

- 献立の各日の材料を、**その日以前で最も近い買い物日**のリストに入れる（その日に買い物があれば当日）。献立より前に買い物日がない場合は、今日のリストに入れる。
- 同じ食材を集約し、`pack` があればパック単位に切り上げる。なければ量をそのまま（g は10g単位に切り上げ）。
- `pantry` の食材はリストに入れず、`pantry` 欄（家にあるか確認）に名前を出す。ただし「醤油切れた」で在庫が none の常備品は、最初に使う日の買い物リストに「〇〇 買い足し」として載せる。
- 惣菜（売り場が deli）は日持ちしないので、その日の分を当日のリストに入れる（帰りに買う）。数日前に買って冷凍させない。
- 在庫を差し引く：plenty → 買わない、some → 半パック分を差し引く、none → 差し引かない。
- 買い物日から調理日までの日数が `shelfLifeDays` を超える食材には、`notes` に「買ったら冷凍」（冷凍できる場合）を付ける。献立のメモは、戻し方（`thaw`）で書き分ける：既定は「前日の夜に冷蔵室へ移して解凍」、貝・きのこ・冷凍野菜・青菜・ねぎ・麺・パン・惣菜（'from_frozen'）は「凍ったまま加熱してください」。
- 売り場順（AISLE_ORDER）、同じ売り場の中は名前順。
- `uncertain` の食材は、リストでも「要確認」を表示する。
- 作り直したときは、同じ買い物日・同じ食材のチェック状態を引き継ぐ。チェックしたときに買った量（ShoppingItem.bought）を記録し、あとで人数や料理が変わって要る量が増えたら、チェックを外して足りない分だけを「さば あと1パック（2切れ）」と出し、メモに「1パック（2切れ）は買ってあります」と添える（返事でも「さばは、買った分では足りなくなりました。買い物リストに「あと1パック（2切れ）」と入れました。」と伝える。足りなくなった物が4つ以上なら、名前は3つまでにして「ごぼう・ほうれん草・合いびき肉など8品は、買った分では足りなくなりました。足りない分を買い物リストに入れました。」のように数を添える）。要る量が減ったときはチェックのまま。「あと」の行をチェックすると前に買った分と合わせた量になり、外すと前に買った分に戻る。過ぎた買い物日のリストの分は、まだ見直さない。
- みんな外で食べる日（夕食なし、servings 0）の材料は、リストに入れない（buildShoppingLists は、servings が古いままでも、家で食べる人のいない日を入れない。家族の変更でみんな外で食べる日になった日は、regenerate_week が servings を0にする）。過ぎた買い物日のリストに残るその日の分は、「まだチェックしていない物」に数えない（家で食べることになったら、また数える）。

### 3-7. 在庫（state.ts / replan.ts）

- 買い物リストでチェック → 在庫に plenty で追加（acquiredOn = 今日）。
- 「作った」→ その日の材料の在庫を1段階下げる（plenty → some → none）。
- 「卵切れた」→ none。「〇〇買った／ある」→ plenty。「〇〇冷凍した」→ 冷凍あり（買った日は変えない）。
- 済んだ形だけを読む：「買ってきて」「買っておいて」「買ってくるね」（頼む・これから買う）、「切れたら」（仮定）、「切れてない」（否定）、「あったっけ？」（質問）では在庫を変えず、今の在庫と買い物リストで答える。
- 返事は、リストが実際にどう変わったかで言う（外れた時だけ「リストからも外しました」。常備品はリストに触れない。日持ちで外れない物は「〇〇まで持たないので、冷凍したら…」）。
- 無反応の日は「作った」とみなさない。翌日に status を 'unconfirmed' にし、「昨日の〇〇は作りましたか？」と1問だけ聞く（[作った] [作らなかった]）。文字で「作った」「作らなかった」「昨日は無理だった」「昨日は外食だった」と答えても同じに扱う。いちばん新しい［作った］のボタンが、まだ答えのない過ぎた日の「作りましたか？」なら（あいだにほかの返事をはさんでもよい。LINE では、前日の確認がその日の最初の書き込みへの返事と一緒に届く）、日の言葉のない「無理だった」「疲れて無理だった」「外食した」「外で食べた」「作れませんでした」は、その日の「作らなかった」にする（今日の「今日は無理」や今日のみんな外食にはしない。LLM の結果より先に見る。いちばん新しい［作った］が有料版の今日の配信や今日のカードのものなら、ここでは扱わない）。答えにしないもの：仮定（「無理だったら別のにして」「外食なら言うね」。ただし「バタバタしてたら作れなかった」のように「たら」のあとが作った・作らなかったで終わる文は、あったことの話として読む）、夕食でない話（給食・お昼・おやつ・お弁当：「給食でカレー食べた」。宿題は「宿題見てて作れなかった」のように作る・作れないと一緒なら夕食の話）、まだ作っていないだけ（「夕飯まだ作ってない」）、1人だけの外食（「パパは外食した」は、今日のパパの欠席として読む）、質問（「誰が作った」）。「外で食べた」「外でカレー食べた」は作らなかった。「今夜は出前にする」「出前とる」は今日を作らない日にする（過ぎた日の答えにはしない）。聞いている確認も「昨日」「今日」「本日」などの日の言葉もないときは、「作った」「作らなかった」だけの答え（「作ったよ😊」「作ったで」「無理やった」も）、作る・作れないで終わる答え（「ママが作った」「しんどくて作れなかった」）、料理の名前や「夕飯」「ごはん」が入った答え（「さばの味噌煮作った」「夕飯作った」）を今日の夕食のこととし、ほかの文（「はるとがおやつ食べた」「パパが資料作った」）では記録しない。「夕飯作った」は「夕飯」で今日の献立を見る命令にも読めるが、作った・作らなかったの答えを先にする（LLM が今日は無理と読んでも同じ。「夕飯」「今日の夕飯なに？」「夕飯作らなきゃ」は、今までどおり今日の献立を見せる）。みんな外で食べた日（夕食なし）は聞かない（status は planned のまま、記録も付けない）。
- 週の振り返りは、記録（作った・作らなかった）のない過ぎた日を「分からない日」（`unconfirmedDays`）として数え、0日とは言わない。記録が1日もなければ数の文を出さず（「今週は5日分の献立でした」）、一部だけなら「記録のあった2日のうち2日、考えずに済みました」と言う。画面の振り返り（週の献立の「先週の振り返り」、トークの振り返りのカード）も同じ数え方で、「記録なし：n日」を添える。みんな外で食べた日（夕食なし）は、献立の日に数えない（作った・作らなかった・記録なしのどれにも入れない）。今日は無理でラク日にした日と作らなかった日は「予定どおり作れなかった日」に数える（今日は無理のあとラク日を作った日は、考えずに済んだ日にも入る）。週末の質問の答えがある週は、「自分で考えた日（週末の質問）：2日／5日」の1行を添える（3-11）。

### 3-8. 組み直し（replan.ts）

- **今日は無理**
  - 今日をラク日に替える（在庫や冷凍で済むものを優先）。
  - 元の料理は翌日以降の空いている日（その週のラク日）と入れ替える。移す先は、旬の月であること、7日以内に同じ主菜がないこと（元の日は数えない）、その曜日の調理時間の上限を超えないこと、その日に食べる人に安全なこと。
  - 移す先がなければ：来週の献立がまだなら「来週の候補に回します」（作らなかった記録で、来週の献立に入りやすくなる）。来週の献立がもうあれば、来週の日（同じたんぱく源を優先）と入れ替える提案を出す（なければ「また近いうちに入れます」）。
  - 冷凍の案内は、もう買ってある傷みやすい食材だけ。移した先の日まで持たないなら「〇〇は〇〇まで持たないので、今夜冷凍してください。冷凍できないときは『〇〇切れた』と送ってください。買い物リストに入れます。」と言い切り、在庫を冷凍にする（同じ物を買い物リストに足して「冷凍して」と「買って」を同時に言わない）。買っていない食材には言わない。組み直しで買い物リストに新しく入った物は、返事で伝える。今日のラク日と、元の料理を移した日は、家族が決めた日（changedBy: user）にする。
  - もともとラク日なら「十分です」と受け止め、［ほかの案］［作らない日にする］を出す。作らない日にしたら、その日の分（まだ買っていない物）を今日以降の買い物日のリストから外し、外したときは「今日の分は、買い物リストから外しました。」と伝える（過ぎた買い物日のリストの分は外さない。3-6 と同じく、まだ見直さない）。トークには押したボタンの文言（「作らない日にする」「ほかの案」）を残す。もともとラク日だった日に今日は無理と言ったときも、その日は家族が決めた日（changedBy: user）にする。
  - 返事は短く、責めない言い方にする。
- **別のに**：その日の候補を2つ出す（点数の高い順、今の料理と違うもの）。選ぶと差し替える（changedBy: 'user'）。「キーマカレー飽きた」のように料理で指したら、その料理の日の候補を出す。候補が1つしかなければ「今日の別の案は、これだけです。この案にしますか？」と聞き、［替える］［そのまま］を出す（Proposal の kind: alternative。替えたら changedBy: user）。
- **押した時点で確かめ直す**：「別のに」の候補・特売や在庫の提案は、作ったあとにほかの日が変わっていることがある。押したときに、安全・旬・7日以内の同じ主菜をもう一度確かめ、だめなら「献立が変わったので、この案は使えません」と新しい候補を出す（リクエストの提案は、頼まれた料理なので7日以内・旬の外でも入れ、返事で知らせる）。
- **特売（〇〇が安い）**：今日以降の献立で、その食材の substitutes を使っている日、または同じたんぱく源の日を探し、その食材を使う料理への差し替えを提案する（Proposal）。なければ、肉なら肉の日、魚介なら魚介の日まで広げる。差し替える料理は、安全・旬・7日以内の重複・前後の日のたんぱく源を見て選ぶ。承諾したら差し替え、買い物リストを作り直す。候補がなければ「来週の候補に入れます」。家族の除外に当たる食材なら「〇〇の除外に当たるので、献立には使いません」と返す（「〇〇買った」も同じ）。日を選ぶときは、家族が自分で決めた日（changedBy が user・sale）を後回しにする。
- **欠席（水曜は夫が飲み会）**：その日の absentMemberIds に追加して servings と買い物リストを計算し直す。
  - 日付は全部読む（「明日と明後日」「水曜と木曜」「週末」「再来週の月曜」）。週を書いた曜日に続けた曜日も、その週の曜日（「来週の水曜と木曜」「来週の水曜、木曜」「来週の月・水」「来週から月曜は外食」は来週、「再来週の月曜と火曜」は再来週。「来週の土日」は来週の週末）。範囲（「明日から木曜まで」「11/10〜11/12」「金曜から月曜まで」、2週間まで）は間の日もすべて、「木曜まで出張」は今日からその日まで、「明日出張で木曜に帰ってくる」は帰ってくる日の前日まで。範囲の中の献立を作らない曜日には何も言わない。人も全部読む（「パパとはるといない」）。
  - 期間（「明日から3日間」「2泊」「1週間」）は、欠席の日数にだけ使う。「3日後」「2週間後」「2週間後の月曜」は日付、「月水金は」「金土日は」は曜日の並び。「3日に1回」「月に1回」「1週間ぶり」「この1週間」と、来月の曜日は日付にしない。「〜はわからない」のように自分の日付を持つ文は、その日だけを「決まっていない」にする。日を決められない時期（「月末」「年末」「お盆」「連休」「来月」「来週」など）だけを書いたときは、今日のことにも週の献立を見せる命令にもせず、献立を変えずに「いつのことか、日付が分かりませんでした。…日付か曜日で送ってください。」と返す。欠席の取り消し（「月末の外食なくなった」「来週はパパいる」）と「無理」（「来週は無理」。「今週は無理」は今日のこと）も同じ。ほかの用件と一緒に書いたときは、ほかの用件を進めて「いつのことか日付が分からないところは、献立を変えていません。…」を1回だけ添える。「かも」が付けば、決まっていない話として返す。LLM の結果も、ルールで読んでこの用件だけなら使わない（今日のことにしないため）。
  - 献立を作らない曜日（土日など）には「献立の日ではありません」と返す（「献立ができたら」とは言わない）。まだ献立のない献立の日（来週の献立を作る前の来週の日など）には「11/18(水)の献立はまだありません。献立ができたら、もう一度教えてください。」と返す（その日の別のに・リクエストも同じ）。人を書かない「明日飲み会」「今日はいらない」「明日の夕飯いらない」は、書いた人（画面の送る人。handleUserText の opts.senderId。「わたし」「自分」も同じ）の欠席にする。わからなければ「明日は、誰が食べませんか？名前だけ送ってください（例：パパ）。」と聞き返し（全員のラク日や別の案にはしない）、名前だけの答え（「パパ」「パパとはると」「みんな」）を、聞いた日の欠席にする。範囲なら1回だけ聞き、答えを聞いた日すべてに使う。聞いた日と人は、bot の聞き返しの文から読む（サーバーは利用者の発言を残さないため）。送る人がわからない「わたし」は、続柄が「わたし」の人。
  - 「夫」「妻」は、ニックネーム（パパ・ママ など）で決まるときだけ使う。役割（わたし／パートナー）から性別は推測しない。決まらなければ、大人のニックネームを挙げて聞き返す。
  - 遅くなるだけ（「水曜ははるとが塾」「部活」「残業」「パパは帰りが遅い」）は欠席にしない。人数も除外もそのまま（除外のある人の分を減らすと、その人が食べられない料理が入るため）で、「家で食べないときは『水曜ははるとはいらない』と送ってください」と返す。「いらない」「食べてくる」まで書けば欠席。人を書かない「今日は帰りが遅い」は今日は無理。「給食」は欠席の語にしない。まだ決まっていない（「明日パパ飲み会かも」「未定」）ときも献立を変えず、決まったときの送り方を返す（「卵切れたかも」は在庫を変えずに答える）。LLM の結果に、ルールで「遅くなるだけ」「決まっていない」と読める人の欠席があれば、使わない。遅くなるだけ・決まっていない範囲（「明日から木曜までパパ残業」）の返事は1つにまとめる（決まった欠席の返事は、日ごとに出す）。
  - 除外のある人がいない日は、その除外がゆるむ（その日に食べる人で判定するため）。欠席の返事と、そのために出せる料理の提案・承諾・候補には「はるとがいない日なので…。予定が変わったら『木曜ははるともいる』と送ってください」と添える。
  - **みんな外で食べる日（夕食なし）**：家で食べる人がいなくなったら（eatingMembers(household, absentMemberIds) が空。乳児だけが家にいる日も含む）、夕食を作らない日として扱う。献立（dishIds）と status はそのまま残し、量・作り方・理由・［作った］［別のに］［今日は無理］は出さず、カード・週の行・返事は「夕食なし（みんな外で食べる）」（カードには「もとの献立：…」）。状態の印（予定・作った など）も付けない。買い物リストから外し、その日の提案は片づける。別のに・リクエスト・特売・在庫の提案はその日を選ばない（日付で頼まれたら「みんな外で食べる日です（夕食なし）」と戻し方を返す）。翌日の「作りましたか？」、有料版の「今日の夕食」と前日の解凍の連絡は送らない。返事には「予定が変わったら『金曜はみんないる』と送ってください。」を添える（今日・明日・6日先までは曜日、それより先は「11/20(金)」の形で、そのまま読み取れる。1人の家族は「外で食べるんですね」「金曜はやっぱり家で食べる」）。過ぎたら、その主菜は作らなかった日と同じく、また献立に入れられる。
  - 欠席を足しても、その日の changedBy（user・sale）は変えない。
- **欠席の取り消し（木曜ははるといる・お泊まりなくなった・金曜はみんないる・金曜はやっぱり家で食べる・外食しない）**：absentMemberIds から外して servings を戻し、その日の料理を食べる人の除外で判定し直す。当たる料理があれば、出せる別の案に替える（なければ注意して［別のに］を出す）。みんな外で食べる日だったなら「みんな家で食べるんですね」と、戻った献立を伝える。日付がなければ、この先で欠席にしている日を探す（書いた人がみんないない日を先に）。日付を書いたとき（「金曜はみんないる」）は、ほかの日の欠席は取り消さない。人を書かない「家で食べる」は、文の終わりが「家で食べる（ます・予定です・ことになった など）」のときだけ読み、「家で食べるのは無理」は読まない。「外食しないといけない」「外食しないか」は取り消しにしない。
  - 日付がなく候補の日が2日以上あれば（「明日パパ飲み会」「木曜もパパ飲み会」のあとの「やっぱり飲み会なくなった」）、どれも取り消さずに「どの日の予定がなくなりましたか？」と聞き、日付だけの答え（「木曜」）で、その日を取り消す。「全部」と答えれば全部。何日も続く予定（出張・旅行・帰省・入院・合宿・遠征・キャンプ・単身赴任）は、同じ人がいない、続いた献立の日の並びが1つだけなら、聞かずにまとめて取り消す。
- **在庫切れ（卵切れた）**：在庫を none にし、今日以降でその食材を使う日を知らせる（次の買い物リストに入る。常備品は「買い足し」として載る）。
- **リクエスト（金曜はカレーがいい）**：その日にその料理（またはそのたんぱく源・ジャンル）を入れる提案をする。日付がなければ明日以降の日から選び、家族が自分で決めた日（自分で替えた・特売で替えた・今日は無理で決めた日）は、ほかに日がないときだけ選ぶ。日付のない料理のリクエストで、その主菜がもう今日以降の予定にあれば、別の日に重ねず「11/12(木)は、もうキーマカレーの予定です。」と返す。
  - 食材を名指ししたら（「明日はさばがいい」）、その食材を使う主菜（なければラク日用の料理）から選ぶ。出せなければ、そう伝えてから同じたんぱく源で選ぶ。
  - あいまいな言い方（「塩焼きがいい」「炒め物がいい」「肉がいい」）は、当たる料理のうち出せるものを最大3つ見せて選んでもらう（1つなら、それを提案する）。
  - **代わりの提案**：頼まれた料理が除外・要確認に当たるときは、名前の近い、出せる料理を提案する（「カレー」→ ルウを使わないキーマカレー）。なければ理由だけ伝える。
  - 旬の外の料理は、入れられるが「〇〜〇月ごろの料理です」と添える。7日以内の同じ主菜は、作った記録なら「〇/〇に食べたばかりですが」、これからの予定なら「〇/〇にも〇〇の予定があります」と日付で伝える。
- **週の作り直し（設定を変えたとき）**：自分で替えた日・特売で替えた日（changedBy が user・sale。今日は無理で決めたラク日と、元の料理を移した日も user）は、安全・旬・献立の曜日にまだ合うかぎり残し、ほかの日だけを作り直す。返事で「自分で替えた日は、そのままです」と伝える。家族が決めたラク日が出せなくなったら、ラク日のまま料理だけを替える。みんな外で食べる日は作り直さず、献立をそのまま残す（家で食べることになったら、その献立に戻す。これからの日がみんな外で食べる日だけなら「作り直す献立はありません」と返す）。
  - 家族の変更（アレルギー・年齢・人の追加や削除）では keepSafe: true で呼ぶ。今の家族でも出せる日は、だれが決めた日でも残し、出せなくなった日だけを作り直す（「11/11(水)は、家族の変更に合わせて作り直しました。ほかの日は、そのままです。」。家族が決めたラク日は「11/9(月)は、ラク日のまま料理を替えました。」。当たる料理がなければ「家族の変更に当たる料理はないので、献立はそのままです。人数と買い物リストは直しました。」）。買ってあった物で足りなくなった物は、返事で伝える。献立の曜日・買い物の曜日・ラク日・新しい料理・副菜・要確認の変更では、keepSafe なしで作り直す。

### 3-9. 会話（conversation.ts）

- **口調**：短く、やさしく、責めない。絵文字は使わない。1メッセージ3〜6行まで。
- **メッセージの組み方**：コマンドごとにカード（Card）とボタン（ActionButton）を付ける。
  - 例：今日の献立 → card: { kind: 'meal' }、ボタン [作った] [別のに] [今日は無理]。
- **わからない書き込み**には、使える書き方の例を3つ返す（見るだけの例「今日のごはん」を1つ入れる）。あいさつ・お礼・おまかせ（「ありがとう」「了解」「何でもいい」）には短く返す（画面の「@きめとく」が付いていても）。アレルギーの話（「はるとはえびアレルギー」）には「アレルギーや食べられない物は、トークでは登録できません。『家族と設定』で家族ごとに登録すると、その食材を使う料理は献立に入れません。」と返す（お客さんの話なら、その日の材料を確かめてもらう）。時間の短い料理の希望（「今日は20分で作れるのがいい」）には［今日は無理］［別のに］を出す。直前の返事の提案や「どちらにしますか？」の案が残っていれば、そのボタンを出し直す。「使い方」にもアレルギーの登録先を1行入れる（例は4つ）。
- **1つの書き込みに用件がいくつかあるとき**：同じ命令は1回だけ（LLM の結果の重なりも）。その日の予定を変える命令（欠席・欠席の取り消し・今日は無理）を先に、日を決めて案を出す命令（日付つきのリクエスト・別のに）を次に、日を選んで案を出す命令（特売・在庫・日付のないリクエスト）と見るだけの命令をあとに処理する（同じ順位の中は書かれた順。返事もこの順）。提案は日ごとに1つなので、同じ返事の中で同じ日に2つ目の案（提案・別の案）は出さない：あとの特売・在庫・リクエストは、案のない別の日を選ぶ。ほかに合う日がなければ「替えられる日（11/13(金)）には、上で別の案を出しています。豚こま切れ肉の案にしたいときは、もう一度『豚こま切れ肉が安い』と送ってください。」と短く伝える（リクエストは「このリクエストにしたいときは、それだけをもう一度送ってください。」、在庫は在庫に入れるだけ）。前の書き込みの提案は、今までどおり置き換わる。
  - 案が2つ出たとき、片方の［替える］か［そのまま］を押したら、その返事に、もう片方の案をボタンつきで出し直す（「もう1つの案も、ボタンで選べます。」）。ボタンは最後の書き込みのあとの返事にしか出ない（LINE のクイックリプライも最後のメッセージだけ）ため。「どちらにしますか？」の別の案を選んだときも、同じ返事のほかの日の提案を出し直し、提案に答えたときは、同じ返事のほかの日の「どちらにしますか？」を「明日の別の案も、ボタンか『1』『2』で選べます。」と出し直す。片方を替えたことで使えなくなった案（同じ主菜が7日以内に入る など）は、出し直さずに取り下げて「11/12(木)の案は、使えなくなりました（酢豚が7日以内に入っています）。」と伝える。
- **直前の返事への文字の答え**（LLM の結果より先に見る。LLM は直前の返事を知らないため）：提案の［替える］［そのまま］には「はい」「お願いします」「替えて」「OK」／「そのまま」「いいえ」「大丈夫です」（今日の返事の提案が2つ以上なら、どれか聞いてそれぞれのボタンを出し直す。あとに前日の「作りましたか？」があれば、そちらへの答え）。「どちらにしますか？」には「1」「2番目で」や料理の名前（ほかの日を書いたら答えにしない）。「誰が食べませんか？」には名前だけ。「どの日の予定がなくなりましたか？」には日付だけ（「全部」も）。
- **書き込みの読み方**（ルールベース）：
  - 否定（「今日は無理じゃない」「外食じゃない」「卵は切れてない」）では変えない（今日の献立や在庫を見せて確かめる）。「無理しない」は「ラクする」の意味として、今日は無理のまま。
  - 仮定（「卵が切れたら」「無理なら」）・質問（「豆腐あったっけ？」「卵ある？」）では、状態を変えずに答える。
  - 過去の日（「昨日は無理だった」「先週は外食が多かった」）では今日を変えない。前日の確認への答えなら、その記録にする。
  - 頼む形（「豆腐買ってきて」）では在庫を変えず、買い物リストの状態を答える。
  - ひらがな2文字の食材（いか・たら・さけ・ぶり など）は、前後が文頭・助詞・ひらがな以外のときだけ読む（「安いから」「たらこ」「さける」に当てない）。
  - ジャンル・たんぱく源の語（「中華がいい」「明日は魚」）は、料理名のあいまいな一致より先に見る（「中華」を冷やし中華にしない）。料理名の一部（「生姜焼き」）は、食材の語をそろえて照合する。
  - 「〇〇飽きた」「〇〇じゃないのがいい」は、その料理の日の別の案。
  - ひらがな2文字の食材は、すぐ後ろが「ある」「あった」でも読む（「さばある？」「サバあったっけ？」）。食材と「ある」の間の量の語（「キャベツ半分ある」「卵2個ある」）も読む。食べ物の絵文字（🍛 など）は言葉にして読む。
  - 「明日の夕飯なに？」「金曜の夕飯なんだっけ」はその日の献立（show_today の date。2日以上なら週の献立）、「今日の夜ごはんなんだっけ」は今日の献立。「明日何買えばいい？」はその日の買い物（show_shopping の date。その日が買い物の日でなければそう伝え、その日の夕食の材料が入っているリストか、次のリストを見せる）。
  - わけを話す文（「昨日カレーだったから今日は別のがいい」の「〜だったから」「〜だったので」）は分けて読む。過ぎた日だけの文があっても、文全体を読み直さない（「昨日は無理だったけど今日は作る」は昨日の記録だけにして、今日は変えない）。「だったら」は過ぎたことにしない。
  - これらのために、ParsedCommand に任意の欄がある（absence の cancel・tentative（late・maybe）、have・out_of_stock の question、have の frozen、request の ingredientId・dishIds、want_alternatives の dishId、show_today・show_shopping の date）。ParseContext には送る人（senderId）を渡せる。LLM は使わなくてよく、使うときも validateCommands で検証する（tentative は受け取らない）。
  - LLM（サーバーと画面の AI の読み取り）の出力の形にも、cancel・question・frozen を入れ、request の ingredientId と want_alternatives の dishId を受け取る（dishIds は使わない）。過ぎた日のこと・打ち消し・仮定の文では、献立を変える命令（today_impossible・want_alternatives・absence）を出さないように頼む（出さなければルールベースが読む）。遅くなるだけ（塾・部活・残業・帰りが遅い）、「かも」、人を書かない欠席（「明日飲み会」「今日はいらない」）でも absence を出さないように頼み、show_today・show_shopping の date を受け取る。前日の確認への答え（「昨日は無理だった」）は、LLM の結果より、ルールでの記録を先にする。show_today・show_shopping に date がない（LLM が落とした・検証で外れた）ときは、ルールが同じ命令を1つだけ日付つきで読めていれば、その日付を使う（handleUserText で直すので、画面も LINE も同じ。「明日の夕飯なに？」に今日の献立を返さない）。
  - LLM の欠席の memberRef に、家族にいない member の id（member_9）や、書き方を変えた id（「member-9」「メンバー9」）、数字のない「member」があれば、その欠席は使わない（返事に id を出さない）。id がいくつか書かれていたら（「member_2とmember_3」）、1人ずつの欠席にする（画面の checkMemberRefs も同じ）。
- **反応**：「作った」のあと、◎○△のボタンを出す（世帯としての反応。有料版はメンバーごと）。有料版は、1人押すたびに、まだ押していない人のボタンを付け直す（全員そろったら「全員分そろいました」）。

### 3-11. 1週間の試用：週末の質問（checkin.ts）

北極星「今週、自分で考えた夕食は何日？」（企画書 12章）を、画面と LINE で同じに聞いて記録する。

- **聞く日**：advanceDay が、その週（月〜日）の最後の献立の日（みんな外で食べる日・料理のない日も含む）の翌日に1回だけ聞く（月〜金の家族なら土曜）。「作りましたか？」のあと、有料版の配信の前に置く。有料版でも配信（push）ではなく、ふつうのメッセージ。週の途中で献立の曜日を減らして最後の献立の日が早まったときも、同じ週のうちなら聞く。答えのある週・もう聞いた週・どの日もみんな外で食べた週には聞かない。
- **数える日**：その週の料理のある献立の日のうち、みんな外で食べた日を除いた日（weeklySummary の plannedDays と同じ数え方）。始めた週は、最初の献立の日からの日だけ。
- **文**：「11/16(月)〜11/20(金)の夕食で、自分で献立を考えた日は何日ありましたか？」「アプリの献立どおりの日や、アプリで替えた日は数えません。」。範囲の中に、みんな外で食べた日があれば「みんな外で食べた日（11/18(水)）も数えません。」を添える。献立の日が続いていない家族（月・水・金など）には、範囲でなく「11/16(月)・11/18(水)・11/20(金)の夕食で…」と日を並べる（献立のない日の夕食まで数えないように）。1日だけなら「11/20(金)の夕食で…」。
- **ボタン**：［0日］…［N日］（N は数える日の数。Action は `weekly_checkin { weekStart, thoughtDays }`）。
- **記録**（applyAction の weekly_checkin と、下の文字の答えで共通）：state.checkins に週ごとに1つ（`{ weekStart, plannedDays, thoughtDays, answeredOn }`。前の版の状態にはないので、ないときは空）。答え直したら置き換える。返事は「ありがとうございます。記録しました（自分で考えた日：2日／5日）。」、違う数なら「答えを直しました（自分で考えた日：3日／5日。前の答えは2日）。」、同じ数なら「もう記録してあります（…）。」。0〜N の外の数は記録せず「0日から5日までで答えてください。」（N が1なら「「0日」か「1日」で答えてください。」）と、ボタンを出し直す。まだ終わっていない週・これからの週は「その週の夕食がまだ終わっていないので、記録できませんでした。」、月曜でない日・献立のない週は「その週の献立が見つからないので、記録できませんでした。」。N は、質問があればそのボタンの数（聞いたときの日数）。
- **文字の答え**（handleUserText。直前の返事への答えと同じく、LLM の結果より先に見る）：週末の質問が、いちばん新しい「答えを待っている質問」のときだけ読む。それより新しい、今日の「どちらにしますか？」・まだ使える提案・答えのない過ぎた日の「作りましたか？」・直前の返事の「誰が食べませんか？」「どの日の予定がなくなりましたか？」があれば、数はそちらへの答えにする（「2」は2つ目の案、「全部」は取り消しの答え）。
  - 読む言い方：「2」「2日」「２日」「二日」「ふつか」「2日です」「たぶん2日」「1日だけ」「3回」、質問をなぞった「2日考えました」「自分で考えた日は2日です」「5日とも」「5日全部」。0日は「0」「ゼロ」「なし」「ない」「なかった」「1日もない」「考えてない」「自分で考えた日はない」、N日は「全部」「毎日」。「いつか」「なのか」と2けたの数（「12日」）は、日付のことがあるので読まない。「2日考えてない」は数にしない。
  - 答えたすぐあと（読み取れなかった返事をはさんでもよい）の数（「やっぱり3」「3日に直して」）は、答え直しにする。数だけで答えられるのは、今週と先週の質問だけ（それより前の週は、返事に週を書かないので、ボタンで答える）。
  - 週の最後の献立の日の翌朝、「作りましたか？」のすぐあとに週末の質問が続くときの「はい」は、前日の「作りましたか？」への答え（週末の質問は「はい」では答えられない）。
- **振り返り**：答えた週の weeklySummary に `checkin { plannedDays, thoughtDays }` を入れ、振り返りのカードの文と、次の週の献立のメッセージ（画面・LINE）に「自分で考えた日（週末の質問）：2日／5日」の1行を添える。見出しは `CHECKIN_SUMMARY_LABEL`（画面の振り返りも同じ見出しで出す）。

### 3-12. 1週間の試用：試用の記録（trial.ts）

家族が試用のあとに主催者へ送る文。名前は入れず、数だけを数える（数え方の細かいところと weeklySummary との関係は、trial.ts の先頭に書く）。

- **形**（`TrialReport`、v: 1）：from・to（数えた献立の日の範囲。まだなければ null）、madeOn（作った日）、clock（calendar：本物の日付／demo：［翌日へ進む］／unknown）、plan、family（年齢帯ごとの人数と、除外のある人の数）、days（dinner・everyoneOut・cooked（＝cookedAsPlanned＋cookedChanged）・skipped・unconfirmed・todayImpossible）、reactions（◎○△）、checkins（週末の質問の答え。新しい8週まで）、safetyViolations と safetyViolationDays（10日まで）、talk（messages：書き込み、unreadable：読み取れなかった書き込み、taps：ボタンを押した数、unreadableTexts：送る人が選んだときだけ）。
- **数える日**：state.meals に残っている料理のある献立の日のうち、過ぎた日と、作った・作らなかったを記録した今日（advanceDay が先週より前の献立を消すので、先週と今週まで）。どの日も everyoneOut・cooked・skipped・unconfirmed のどれか1つに入る（dinner はその合計）。dinner − everyoneOut は weeklySummary の plannedDays、cooked は decidedWithoutThinking と同じ。反応は、その範囲の記録から数える。
- **そのまま／替えて**（作った日の内訳）：家族が替えた日（changedBy: user。別のに・リクエスト・今日は無理のラク日）と特売で替えた日（sale）は「替えて」、アプリの献立どおりの日とアプリが組み直した日（replan・absence。在庫の提案に替えた日も）は「そのまま」。今日は無理で元の料理を移された日は「そのまま」（その日について家族は何も選んでいない）。もともとラク日の日の「今日は無理」は「替えて」。todayImpossible は、今日は無理で実際にラク日に替えた日（作らなかった記録が残る日。ほかの数と重なる）。
- **除外の違反**：その日に食べる家族の除外に当たる料理の数（範囲の始めから、この先の献立まで）。過ぎた日は、その日が終わったとき（advanceDay）に確かめた数（`PlannedMeal.safetyAtDayEnd { dishIds, excluded }`）を使い、今日とこれからの日は今の家族で確かめる（週の途中で家族や除外を足しても、足す前に過ぎた日を違反にしない）。
- **トーク**：ボタンを押した発言（`ChatMessage.tap`。applyAction が付ける）は書き込みに数えず、taps に数える。読み取れなかった書き込みは、`UNREADABLE_REPLY`（「すみません、うまく読み取れませんでした。」）の返事のすぐ前の書き込み（画面が AI に頼むかを決めるときも、この書き出しで見分ける）。
- **送る文**（formatTrialReport）：読める行（「きめとく 試用の記録（11/21(土)に作成）」「期間：11/16(月)〜11/20(金)（カレンダーどおり）」「家族：大人2・小学生1・幼児1（除外のある人 1人）／無料版」「献立の日」「作った」「「今日は無理」でラク日にした日」「週末の質問」「家族の反応」「除外の違反」「トークの書き込み」）と、最後の1行「きめとく試用データ:{JSON}」。集計ページは、印（`TRIAL_REPORT_MARKER`）のあとの JSON を読む。読める行と JSON は、いつも同じ中身にする。
- **大きさと名前**：4,500字まで（`TRIAL_MAX_REPORT_LENGTH`。LINE の1通は5,000字）。超えるときは、読み取れなかった書き込みの文を古いものから外し、それでも超えれば古い週の答えを外す。読み取れなかった書き込みの文は、送る人が選んだとき（includeTexts、既定 false）だけ入れる。入れるときは NFKC にして、先頭の「@きめとく」・制御文字・見えない文字を外し、家族の呼び名を「〇〇」に置き換え（かな・カタカナ・全角半角・大文字小文字を区別しない。かな1文字の呼び名は置き換えない）、記録の印は全角のコロンにして、1件60字・新しい順に20件まで（同じ文は1つ）。
- **読む**（parseTrialReports）：貼り付けた文から、印ごとに記録を取り出す（何家族分を続けて貼ってもよい。あいさつなどが混ざってもよい）。JSON は { } の対で切り出し、読めなければ、メッセージアプリが入れた改行（CR だけ・行区切り文字も）と幅のない文字を外して、さらに LINE のトーク履歴の書き出し（" が "" になる）を戻して読む。形は checkTrialReport で確かめ（日付・期間・日数の合計・thoughtDays ≤ plannedDays・unreadable ≤ messages など）、使えないものは「2件目：記録の数字の行を読めませんでした（途中で切れているかもしれません）」のように、何件目かとわけを返す。印のコロンが全角のものは読まない（読める行の文に入った印と見分けるため）。

## 4. UI（src/ui）

- **見た目**：スマホ幅（360〜430px）を基本にし、PC では中央に置く。LINE のトーク画面に似せた「献立」グループと、LIFF に似せた画面（週の献立、買い物リスト、設定）。
- **画面**
  1. **初回設定**：①家族（ニックネーム、年齢帯、除外食材・アレルギー、重いアレルギーの印）②買い物の曜日 ③定番（マスタから検索・選択、自由入力も可。自由入力の名前にもマスタの料理と同じく「除外」「要確認」の印を付け、名前が除外に当たる料理は加えられない）④無料／有料の切り替え。「デモの家族で始める」ボタンも置く（今の状態から開いたときは、ページの中で「今の家族と記録は消えて、デモの家族で始め直します。元には戻せません。」と確かめてから置き換える。確認の画面の注意にも「今の家族と記録は、この内容で置き換わります。」を書く）。確認（⑤）には「本物の日付で進める（1週間の試用）」のチェック（既定は印あり。説明「印を外すと、画面の［翌日へ進む］で日付を進めるデモになります。」）を置き、印があれば日本時間の今日から本物の日付で、なければ［翌日へ進む］のデモで始める（「デモの家族で始める」は、いつもデモ）。続柄の既定は、1人目がわたし、2人目がパートナー、3人目からは子ども（小学生）。子どもの年齢帯を選ぶと、わたし・パートナーは子どもになり、大人を選ぶと、子どもはその他になる（大人の子どもなら、続柄を選び直せる）。年齢を選び直して元の続柄が合うようになれば、元の続柄に戻す（家族と設定でも同じ）。
  2. **トーク**：bot のメッセージ、カード、ボタン。入力欄（「@きめとく」付きで送る）。下にリッチメニュー（今週の献立／今日のごはん／買い物リスト／設定）。カードは今の state から描くので、トークの古い1日・週のカードは、あとで同じ日（週）のカードが届いたら畳んで「いまの献立を見る（日付）」にする（最新のカードはそのまま出す）。ボタンは、最後の書き込みより後のメッセージにだけ出す。ただし、週末の質問の［0日］…（その週の答えが入るまで）と、まだ答えのない過ぎた日の［作った］［作らなかった］（その日の記録が入るまで）は、ほかの書き込みのあとも出しておく。どちらも、その週・その日のボタンのある、いちばん新しいメッセージにだけ出す（shownActions。週末の質問のボタンは、1つ 52px 以上の幅で、狭い画面では折り返して並べる）。同じ名前のボタンが2つ以上のメッセージにあるときは、今日でない日の分に日付を付ける（週末の質問の［0日］…は、その週の月曜の日付。LINE のクイックリプライと同じ）。過ぎた日の献立を替えるボタン（［別のに］［今日は無理］、別の案）と、みんな外で食べる日の［作った］［作らなかった］［別のに］［今日は無理］と、もうない提案（日が過ぎた・作り直しで片づいた提案）の［替える］［そのまま］は出さない（LINE と同じ）。時刻は、同じ日の中で前のメッセージより早くならないように出す。
  3. **今週の献立**：日ごとの料理、時間、理由、注意。各日に［差し替え］、今日なら［今日は無理］、過去の日には［作った］と反応。今日の行には「今日」の印を付ける。メニューから開いたとき、今週の献立日が残っていなくて来週の献立があれば来週を開き、終わった今週の振り返りを上に出す（［今週］で戻れる）。トークに残る先週の週のカードからは先週の献立を開き、未確認の日に［作った］［作らなかった］を押せる（献立の残っていない、もっと前の週のカードにはボタンを出さない）。量は「4人分（大人換算3.2）」と出し、小学生・幼児のいる家族には換算の説明を1行出す。新しい料理には「作り方は、料理名でレシピを探してください」と添える。みんな外で食べる日（家で食べる人がいない日）は、量・作り方・理由の代わりに「夕食なし（みんな外で食べる）」と出し、もとの献立を小さく添える。この日には［作った］［作らなかった］［今日は無理］［差し替え］と状態の印（予定・作った など）を出さない（トークの1日のカード・週のカード・返事のボタンも同じ）。
  4. **買い物リスト**：買い物日ごとのタブ、売り場ごとのまとまり、チェック、常備品の確認、「買ったら冷凍」の印。済んだ買い物日のタブとトークの買い物のカードの「のこり」は、まだチェックしていない物のうち、これからの献立に使う物（みんな外で食べる日の分を除く）だけを数え、済んだ日のリストにはそう説明する。買ったあとで要る量が増えた物は、足りない分だけをチェックなしで出す（「さば あと1パック（2切れ）」と、メモ「1パック（2切れ）は買ってあります」）。
  5. **設定**：家族と除外、買い物の曜日、うちの定番（一覧。除外に当たる・要確認で献立に出ない定番には、そのわけを添える。追加・削除はまだない）、プラン、日付の進め方、AI の読み取り、注意書き、データ（試用の記録、書き出し・読み込み（JSON））、リセット。家族のニックネーム・続柄だけを直したときは献立を作り直さない。年齢帯・除外の変更と、家族を加える・外すときは、今の家族で出せなくなった日だけを作り直す（regenerate_week の keepSafe。知らせもトークの返事と同じく「11/13(金)は、家族の変更に合わせて作り直しました。ほかの日は、そのままです。」（家族が決めたラク日は「11/9(月)は、ラク日のまま料理を替えました。」）か「家族の変更に当たる料理はないので、献立はそのままです。…」）。献立の曜日・買い物の曜日・ラク日・新しい料理・副菜・要確認の変更では、自分で替えた日を残して週を作り直す（これからの日がみんな外で食べる日だけなら作り直さない）。乳児（1歳未満）の除外は献立に使わないので、カードと入力欄にそう書き、乳児の除外だけを直したときは献立を作り直さない。家族を加えたときは、加える前に過ぎた「みんな外で食べた日」に、加えた人も欠席として入れる（振り返りと試用の記録は過ぎた日も今の家族で数えるので、その日が「記録なし」に変わらないように）。リセットでは、画面の設定（AI の読み取り・メニューの開閉・案内を開いたか）も既定に戻す（日付の進め方は［翌日へ進む］のデモ）。
     - **日付の進め方**：「本物の日付で進める（試用）」（「日付は、日本時間の今日に合わせて毎日進みます。1週間の試用は、こちらを選んでください。」）と「［翌日へ進む］で進める（デモ）」（「画面の上の［翌日へ進む］を押すと、1日進みます。」）。記録の日付が今日より先なら本物の日付には切り替えず、その場で「記録の日付（11/20(金)）が今日より先に進んでいるので、切り替えられません。［はじめから設定する］で、今日から始め直してください。」と出す。今日より前なら、切り替えてすぐに追いつく（「本物の日付で進めます。11/19(木)まで日付を進めました。」）。
     - **試用の記録**（データの欄の先頭）：説明「1週間の試用のあとに、この記録を主催者に送ってください。名前は入らず、数だけをまとめています。LINE やメールに貼り付けて送れます。」、チェック「読み取れなかった書き込みの文も入れる（読み取りの改善に使います）」（既定は印なし）、送る文の欄（読むだけ。formatTrialReport(trialReport(state, catalog, { includeTexts, clock }))。シートを開いている間だけ作る）、［コピー］（押したときの処理の中でクリップボードに書く。使えない・断られたときは、欄を選択して「コピーできませんでした。テキストを選択してコピーしてください。」）。
     - データを読み込んだとき、本物の日付で進めていて、記録の日付が今日より先なら［翌日へ進む］のデモにし（「読み込みました。記録の日付（11/20(金)）が今日より先なので、［翌日へ進む］で進めるデモにしました。」）、今日より前なら追いつく。
- **案内**（「このプロトタイプについて」）：PC（幅 900px 以上）では左に置き、スマホ幅では「?」で重ねて開く（開いている間は、ほかの操作はできない。幅が 900px 以上になったら閉じて、フォーカスを左の案内の見出しに移す）。「試してほしいこと」の先頭に［はじめから設定する］を置く。スマホ幅では、案内を一度開くまで、デモの操作に［試し方を見る］を出す（自動では開かない）。AI の段落は、AI の読み取りの設定で変わる。
- **デモ操作**：画面上部に「今日の日付」と［翌日へ進む］（AI の読み取り中は押せない）。本物の日付で進めるときは、見出しを「今日」にし、［翌日へ進む］の代わりに「本物の日付で進めています（試用）」と書く（プランの切り替えと「?」はそのまま。領域の名前は「日付とプラン」）。
- **日付の進め方**（画面だけの設定 UiPrefs.clock：'calendar' か 'demo'。既定は demo。保存した状態がなくデモの家族で開くときは、いつも demo）：calendar では、開いたとき・画面に戻ったとき（visibilitychange）・ウィンドウに戻ったとき（focus）・1分ごとに、記録の日付が日本時間の今日（japanToday）より前なら、今日まで advanceDay を繰り返す（catchUpTo。1回に31日まで。まとめて1回だけ保存し、知らせは1つ：「11/17(火)になりました。」「11/19(木)まで日付を進めました。」、有料版は「配信がN件届きました。」を添える）。AI の読み取り中は進めず、その書き込みの返事を入れてから進める。記録の日付が今日より先でも戻さない。トークの時刻は出さない（エンジンの時刻は日付と採番から作る目安で、本物の時刻と合わないため。日の区切りは出す）。案内の［翌日へ進む］の手順は「次の日に…」の言い方にし、デモの家族（卵アレルギー）だけに当てはまる説明は出さない。プランを有料にしたときの知らせは「有料版にしました。次の日から、配信が届きます。」。
- **AI の読み取り**（任意。設定は「おまかせ（ルールで読めないときだけ AI）」「いつも AI」「使わない」）：Artifact の中では見ている人の Claude、開発時はサーバーの `/api/parse` を使う。送る前に、家族の名前を `member_1` などに置き換える（ひらがな・カタカナ・全角半角・大文字小文字の書き分けも。1文字の名前は、かなでないとき（漢字・英字など）だけ。サーバーも同じ決まり）。読み取りの間に家族やデータが入れ替わったら（リセット・読み込み・はじめから設定・デモで始め直す・家族を外す）、その結果は使わずに知らせる。使えないときは、ルールで読み取る。おまかせでは、命令が読めた書き込みと、前日の確認への答え（作った・作らなかった・昨日は無理だった）、12文字以下のあいさつ・お礼は AI に送らない（エンジンの handleUserText を、送る人も渡してルールだけで試して決める）。session_expired は、その書き込みをルールで読んで「ログインし直すと、また AI で読み取れます」と1回知らせ、AI は止めない（自分では再試行しない）。家族にいない member の id を指す欠席は捨て、id がいくつかなら1人ずつに分ける。AI の結果は、画面だけが知っていることで整えてからエンジンに渡す（prepareAiCommands：「俺」「わたし」など書いた人自身の欠席は送る人の欠席に、見るだけの命令で AI が日付を落としたら、ルールで読んだ日付を使う。エンジンの handleUserText も同じ決まりで直す）。名前のかなを含むよくある言葉（そのまま・わがまま・〜したまま・ぱぱっと など）は置き換えない（サーバーも同じ）。
- **送る人**：トークの「送る人」（大人から選ぶ）を、エンジンの handleUserText に opts.senderId として渡す。人を書かない「明日飲み会」「今日はいらない」は、送る人の欠席になる。送る人を家族から外したときと、データを読み込んだときは、最初の大人に戻す（外した人の発言は、外したときの名前で出し続ける）。
- **状態の保存**：localStorage（try/catch で包み、使えなくても動く）。保存できないときは、データの欄にそう書き、本物の日付で進めているときは一度だけ「このブラウザには保存できません。ページを閉じると、家族と記録が消えます。」と知らせる。同じページを2つのタブで開いたときは、日付を進める前と storage イベントで保存を読み直し、ほかのタブがあとから保存した記録（日付の進め方・送った人の覚え書きも）を使う（古いタブが古い記録で上書きしない。読み取り中の AI の結果は使わない）。
- **文言**はすべて日本語。注意書き（householdNotices）は設定と初回に必ず見せる。
- **アクセシビリティ**：押せる所は 44px 以上（曜日のボタンは、7つ並ばない幅では2段にする。買い物のチェックは、行の左の列のどこを押しても切り替わる）。色だけに頼らない（今日の行は「今日」の印と aria-current、選べない料理は「除外」の印）。シートや案内を閉じたら、開いたボタンにフォーカスを戻す。幅が変わってフォーカスのある所が隠れたら、同じ案内のある見える所に移す（広くなったら左の案内の見出し、狭くなったら「?」、初回設定の画面ならその見出し）。案内を重ねて開いている間は、ほかの操作に Tab で移らない。重いアレルギーの印と「要確認の料理も出す」は、行のどこを押しても切り替わる。トークの入力欄は、「@きめとく」を押しても入れる。

## 5. サーバー（server）

- **Hono（@hono/node-server）**
  - `GET /health`
  - `POST /api/parse` `{ text, today, members }` → `ParsedCommand[]`（開発用。`PARSE_API_ENABLED` のときだけ使える。既定は 404。`CORS_ORIGIN` にない Origin は 403、JSON でない本文は 415 で、LLM を呼ぶ前に断る）
    - `ANTHROPIC_API_KEY` があれば LLM を使い、なければ、または失敗したらルールベース。
  - `POST /line/webhook`：LINE の Messaging API。
    - 署名（x-line-signature、HMAC-SHA256）を必ず検証する。
    - 送り元（userId / groupId）ごとに状態を JSON ファイルに保存する。発言の原文は保存しない（利用者のメッセージの text は空にする）。unfollow（ブロック）・leave（退出）で、その送り元の記録を消す。
    - 同じ送り元の更新・削除は、プロセスの中のロックで1つずつ順に行う（書き込みは一時ファイルから rename）。複数のプロセスから同じ `DATA_DIR` を使うことは想定していない。
    - テキストは、1対1のトークでは全部処理する。グループでは「@きめとく」で始まるか、bot がメンションされた発言だけを処理し、それ以外は保存もしない。
    - postback は Action の JSON として処理する（週末の質問の `weekly_checkin` も。thoughtDays は 0〜7 の整数だけ受け付ける）。
    - 返信は reply API（応答メッセージ。通数に数えない）。ボタンは最後のメッセージのクイックリプライ（13個まで。メッセージ単位で入れ、組を割らない）。同じ名前のボタンが2つ以上のメッセージにあるときは日付を付ける（今日の分には付けない）。もうない提案のボタン（同じ返信の中で、あとの提案に置き換わった・使えなくなって取り下げた提案など）と、みんな外で食べる日の［作った］［作らなかった］［別のに］［今日は無理］、答えのある週の週末の質問の［0日］…は出さない（画面と同じ）。
    - まだ答えのない質問のボタンは、返信の最後に添え直す（openQuestionMessages。画面が答えるまでボタンを残すのと同じで、クイックリプライは次のメッセージで消えるため）：答えのない週末の質問（今週と先週の分。数だけの書き込みで答えられる範囲と同じ）と、今日・きのう聞いた過ぎた日の「作りましたか？」。ほかの話の返信に添えるので、ラベルにはいつも日付を付ける（「11/9(月) 2日」「11/13(金) 作った」）。返信のボタンのあとに、組を割らずに13個に入るときだけ入れ（週末の質問を先に）、返信に同じボタンがあれば添えない。夕方の配信（push）には添えない。
    - 週末の質問は、「作りましたか？」と同じく同期（syncRecord）でできたふつうのメッセージとして届ける（無料版は次の返信の先頭、有料版は夕方の配信）。同期で前の日の分は届けないが、週末の質問だけは、出た日に届けられなかったら（その日に書き込みがなかった無料版など）、まだ答えがなければ次の返信の先頭に1回だけ添える（いちばん新しい1つ）。
  - `POST /cron/evening`（共有シークレット必須。毎日、土日も呼ぶ）：有料の世帯に「今日はこれ」を push する。文面は送る直前の献立で作り直す。届けそびれた週の献立は、その週が終わるまで残し、今日の言い方で送る（試作版の LINE の世帯はデモの家族＝無料版で作り、切り替える方法がないので、いまは対象がない）。
- **LLM**（server/llm.ts）
  - 公式SDK（@anthropic-ai/sdk）の `messages.parse` と zod のスキーマで、ParsedCommand[] を受け取る。スキーマは平らな形（type・date・memberRef・ingredientId・dishId・protein・genre・cancel・question・frozen。使わない項目は null）。
  - モデルは環境変数 `KIMETOKU_MODEL`（既定 `claude-opus-5-5`）。
  - 1回の解釈は、全体で12秒まで（再試行を含む。サーバーを止めるときは途中でやめる）。max_tokens は 4096（既定のモデルは思考を止められず、思考のトークンも max_tokens に数えるため、出力の JSON より余裕をとる）。断られた・上限で切れた・JSON でない・形が違う、をログで見分ける（本文は出さない）。
  - 出力は必ず検証する（食材 id がマスタにあるか、日付が正しいか）。だめならルールベースに戻る。
  - 名前は送らない。本文の名前は「member_1」などの id に置き換え（ひらがな・カタカナ・全角半角・大文字小文字の書き分けも。1文字の名前は、かなでないときだけ。名前のかなを含むよくある言葉（そのまま・わがまま・〜したまま・ぱぱっと など）は置き換えない。画面と同じ）、メンバーは id・年齢帯・続柄で渡す。
- **環境変数**：`LINE_CHANNEL_SECRET`、`LINE_CHANNEL_ACCESS_TOKEN`、`ANTHROPIC_API_KEY`（任意）、`KIMETOKU_MODEL`（任意）、`CRON_SECRET`、`DATA_DIR`（既定 .data）、`PORT`（既定 8787）、`HOST`（未設定なら、すべてのアドレス。`PARSE_API_ENABLED` のときは 127.0.0.1）、`PARSE_API_ENABLED`（`/api/parse` を使う。既定は無効）、`CORS_ORIGIN`（`/api/parse` を許すオリジン。既定 http://localhost:5173）。

## 6. 受け入れ条件

- デモの家族（大人2、小学生1、幼児1。子どもの1人が卵アレルギー）で、次が成り立つ（テストで確かめる）：

## 7. 試用の集計ページ（src/report）

主催者が、家族から届いた試用の記録（3-12）をまとめて貼り付け、家族ごとの数と、企画書 12章の続行の目安を見るページ。家族は使わない。アプリとは別の1枚のページ（report.html）で、`npm run build:report`（`vite build --mode report` → `scripts/make-report.mjs`）が dist-artifact/kimetoku-report.html を作る（形と検査は make-artifact.mjs と同じ。src/report・src/engine・src/ui/styles.css に、使ってはいけない API や予約されたハッシュがないかも見る）。

- **構成**：数えるのは純粋関数（aggregate.ts。記録の読み取りはエンジンの parseTrialReports）、共有する文（summary.ts）、保存（storage.ts）、画面（ReportPage.tsx）、見本の記録（sample.ts。エンジンで作った記録の写しで、11/2 に始めた家族。記録の形を変えたら作り直す）。見た目はアプリの styles.css のトークンと部品（.btn・.text-input・.confirm・.badge など）をそのまま使い、report.css は色を作らない（styles.css のクラス名を変えると、集計ページの見た目も変わる）。
- **貼り付け**：何家族分を続けて貼ってもよい。家族A・家族B…は貼り付けた順（Z の次は AA）。中身がすべて同じ記録は1つにまとめ、まとめた数を知らせる。読めなかった記録は、エンジンのわけ（「4件目：…」）と「途中で切れているときは、その家族に、記録をもう一度送ってもらってください。」を出す。印の行がなければ、そう知らせる。
- **家族ごと**：名前（任意。このブラウザにだけ保存し、共有する文には入れない）、［外す］［戻す］（外した記録は数に入れない）。［すべて消す］は、ページの中で確かめてから消す（window.confirm は使わない）。貼り付けた文・名前・外した記録は localStorage の `kimetoku-report`（アプリの `kimetoku:v1` とは別）に、try/catch の中で保存する（使えなければ、そう書いて、保存せずに動く）。
- **続行の目安**（目安・今の値・目標・判定）：提案の70%以上を作る＝Σ作った日 ÷ Σ（献立の日 − みんな外で食べた日）（記録なしの日は作らなかった日として数える）、自分で考えた日が半分以下＝Σ自分で考えた日 ÷ Σ聞いた日（週末の質問に答えた家族の数も出す）、除外の違反0件（1件でもあれば「届いていない」）。数える家族が3組（MIN_FAMILIES）より少ないか、日数が合わせて12日（MIN_DAYS）より少ないうちは「まだ分からない」。割合は目安の向きに丸める（「以上」は切り捨て、「以下」は切り上げ。比べるのは整数のかけ算）。表の下に「4週継続60%以上・前払い5組以上は、1週間の試用では測れません。」。
- **北極星**：考えずに済んだ夕食の割合＝1 − 自分で考えた日 ÷ 聞いた日（目標 80%・最低 50%）。全体と家族ごとに出す。
- **家族ごとの表**：家族、期間、日付の進め方、家族構成、献立の日、作った（そのまま／替えて）、作らなかった、記録なし、みんな外食、自分でラク日にした日、週末の答え、反応 ◎○△、除外の違反、読み取れなかった、と合計の行。狭い画面では表の箱の中だけを横に動かす（家族の列は動かない）。
- **気をつけること**（家族ごと）：見本の記録、［翌日へ進む］で進めた記録（「［翌日へ進む］で進めた記録です。本物の日付ではありません。」。数には入れたまま、外すかは主催者が決める）、除外の違反（日付つき）、まだ過ぎた献立の日がない、記録なしが多い（2日以上で30%以上）、週末の質問にまだ答えていない、同じ家族の前の記録かもしれない（家族構成・始めた日・プラン・日付の進め方が同じで、どの数も減っていない記録。「かもしれません」と知らせるだけ）。
- **読み取れなかった書き込み**：家族ごとの数と、送る人が入れた文（家族の呼び名は「〇〇」）。文の入っていない記録は「文は入っていません」。
- **共有**：［集計を文にしてコピー］で、続行の目安・北極星・家族ごとの数を、名前を入れずに（家族A・家族B…で）文にしてコピーする（押したときの処理の中で書く。使えないときは、選択した文の欄を出す）。
