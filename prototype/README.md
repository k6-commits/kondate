# きめとく（仮）― うちの献立当番　プロトタイプ

献立を「作る」AIではなく、「回す」AI。家族がふだん食べている定番料理を覚えて、買い物日に合わせて平日の夕食と買い物リストを先に決めておく。何もしなければそのまま確定し、予定が崩れたら1タップで組み直す。

- 企画：[../docs/app-proposal.md](../docs/app-proposal.md)
- 設計とエンジンのルール：[DESIGN.md](DESIGN.md)

このプロトタイプは、企画の中核の体験を触って確かめるためのもの。本物の課金、ネイティブアプリ、写真からの在庫登録、特売データとの連携、栄養の数値は作っていない。

## 確かめたい体験（DESIGN.md 1章）

1. 3つの質問と定番料理で、すぐに今週の献立が出る
2. 何もしなければ確定。差し替えは2択だけ
3. 正確な買い物リスト（売り場順、パック単位、買い物日ごと）
4. 「今日は無理」で1タップ組み直し
5. 「@きめとく 鶏むねが安い」などの書き込みで献立が変わる
6. 家族の反応（◎○△）で、次の週の提案が変わる
7. 除外食材とアレルゲンの判定、「要確認」、注意書き

## 動かし方

Node.js 22 で確かめている。コマンドはこのフォルダ（`prototype/`）で実行する。

```sh
npm install
npm run dev              # 画面（http://localhost:5173）
npm test                 # テスト（Vitest）
npm run typecheck        # 型の検査
npm run build            # 画面のビルド（dist/）
npm run build:artifact   # claude.ai の Artifact として公開できる1枚のページ（dist-artifact/kimetoku.html）
npm run server           # サーバー（http://localhost:8787）
npm run check            # typecheck・test・build・build:artifact を全部
```

- `npm run build:artifact` は、エンジンも画面も1つの HTML に入れた版（`npm run build:single` の dist-single/）から、Artifact 用のページを作り、大きさや外部の読み込みがないかを検査する。
- 画面だけなら、サーバーも API キーもいらない。状態はブラウザの localStorage に保存する（使えない環境でも動く）。
- サーバーの設定は [.env.example](.env.example) を `.env` にコピーして書く。

## 試してほしい流れ

1. `npm run dev` で開く。保存した状態がなければ、デモの家族で始まった状態で開く（自分の家族で試すときは、案内「このプロトタイプについて」か「家族と設定」の［はじめから設定する］）。スマホ幅では、案内を一度開くまで、上に［試し方を見る］が出る。
   デモの家族は大人2・小学生1（卵アレルギー）・幼児1、買い物は月・木（[src/data/demo.ts](src/data/demo.ts)）。今週の献立と、注意書きが出る。初回設定の「デモの家族で始める」は、今の家族と記録を置き換える前に、ページの中で確かめる。
2. トークで「@きめとく 今日は無理」と送る。
   今日がラク日になり、元の料理はその週のラク日と入れ替わる（旬・7日以内の重複・その曜日の調理時間も確かめる）。移せる日がなければ来週の候補に回し、来週の献立がもうあれば、来週の日と入れ替える案を出す。買ってある傷みやすい食材には、冷凍の案内が付く。
3. 「@きめとく 鶏むねが安い」と送る。
   鶏肉の日（なければほかの肉の日）を、鶏むね肉を使う料理に替える提案が［替える］［そのまま］のボタンつきで出る。替えると買い物リストも直る。
4. 「@きめとく 水曜は夫が飲み会」と送る。
   水曜の量が「4人分（大人換算3.2）」から「3人分（大人換算2.2）」に減り、買い物リストの量も減る（量は、大人・中高生を1人分、小学生を0.7人分、幼児を0.5人分として計算する。大人だけの家族は「2人分」とだけ出す）。「夫」「妻」は、ニックネーム（パパ・ママ など）から分かるときだけ使い、分からなければ誰かを聞き返す。
   「木曜ははるとがいない」のように除外のある人がいない日は、その人の除外を外して判定し、返事でそう知らせる。予定が変わったら「木曜ははるともいる」で元に戻る。
5. 買い物リストを開く。
   買い物日ごとに、売り場順・パック単位で並ぶ。調味料などの常備品は「家にあるか確認」に出る。チェックした物は在庫に入る。
6. 画面上部の［翌日へ進む］を押す。
   「昨日の〇〇は作りましたか？」と1問だけ聞かれる（「作った」「作らなかった」と書いて答えてもよい）。［作った］を押すと、◎○△のボタンが出る。◎の料理は出番が増え、△の料理はしばらく出にくくなる。記録のない日は、週の振り返りで「0日」とは数えない。
7. 画面上部のプランを「有料」に切り替えて、［翌日へ進む］を続ける。
   平日は「今日はこれ」の配信、来週の献立は最初の買い物日の前日に配信（終わった週の振り返りつき）、冷凍した食材を使う日の前日には、その料理の名前で解凍の連絡が届く（凍ったまま加熱する物は除く）。◎○△は一人ずつ押せる。無料版は配信せず、今週の献立・今日のごはんはメニューから開く（解凍の連絡はない）。

書き込みは「@きめとく」がなくても読み取る。ほかにも、次のような書き方が使える。

- 見る：「今日のごはん」「今週の献立」「買い物リスト」「使い方」
- 在庫：「卵切れた」「豆腐買った」「鶏もも冷凍した」。常備品の「醤油切れた」は、次の買い物リストに「買い足し」として載る。
- 聞く・頼む：「豆腐あったっけ？」「豆腐買ってきて」は在庫を変えず、今の在庫と買い物リストで答える。打ち消し（「卵は切れてない」「今日は無理じゃない」）、仮定（「卵が切れたら」）、過ぎた日のこと（「昨日は外食だった」）でも、献立や在庫は変えない。
- 替える：「別のに」「キーマカレー飽きた」「金曜は魚がいい」「明日はさばがいい」「中華がいい」。「塩焼きがいい」のようなあいまいな言い方には、当たる料理から選んでもらう。
- 欠席：「水曜は夫が飲み会」「明日と明後日はパパが出張」「水曜はパパとはるとがいない」「金曜はみんな外食」、取り消しは「木曜ははるといる」。献立を作らない曜日（土日など）には「献立の日ではありません」と返す。

画面のふるまい（試すときに気づきやすいところ）：

- 案内「このプロトタイプについて」は、PC では左に、スマホ幅では「?」で重ねて開く（幅が広くなったら閉じる）。
- トークのカードは、いまの献立で描く。あとで同じ日（週）の新しいカードが届いたら、古いカードは畳んで「いまの献立を見る（日付）」にする。
- 新しい料理（週1品）には「作り方は、料理名でレシピを探してください」と添える（アプリは作り方の本文を持たない）。
- メニューの「今週の献立」は、今週の献立日が終わっていて来週の献立があれば、来週を開く（終わった週の振り返りつき。［今週］で戻れる）。トークに残る先週のカードからは先週の献立を開き、記録のない日に［作った］［作らなかった］を押せる。
- 「家族と設定」には、うちの定番の一覧が出る（除外に当たる・要確認で献立に出ない定番には、そのわけを添える）。ニックネーム・続柄だけを直したときは、献立を作り直さない。リセットは、AI の読み取りの設定なども既定に戻す。

## しくみ

```
prototype/
  src/engine/      献立エンジン（純粋な TypeScript。DOM も Node API も使わない）
    types.ts       すべての型（画面・サーバー・エンジンの契約）
    index.ts       公開API。画面とサーバーはここからだけ import する
  src/data/        料理マスタ・食材マスタ・アレルゲン・デモの家族
  src/ui/          React の画面（スマホ幅。状態は localStorage）
  src/acceptance/  本物のマスタとデモの家族での受け入れテスト
  server/          Hono のサーバー（LINE の webhook、LLM での読み取り、JSON ファイルの保存）
  scripts/         Artifact 用のページを作るスクリプト
```

- **engine**：すべて純粋関数。入力の state を書き換えず、新しい state を返す。乱数は世帯と週から作る seed で決まるので、同じ入力なら同じ献立になる。献立は点数（定番、家族の反応、7日以内の重複、前日のたんぱく源、旬、在庫、調理時間 など）をつけて日に割り当て、足りなければ条件を段階的にゆるめる。安全・旬・7日以内の重複はゆるめない。
- **data**：日本の家庭の定番料理と、食材（売り場・パック・日持ち・派生原材料を含むアレルゲン・旬・代わりの食材）。
- **ui**：LINE のトーク画面に似せた「献立」グループと、週の献立・買い物リスト・設定の画面。日付は［翌日へ進む］で動かす。
- **server**：LINE の webhook を受けて、送り元（ユーザー・グループ）ごとの状態を JSON ファイルに保存し、エンジンで処理して返信する。

### LLM を使うところ・使わないところ

| コード（エンジン）で決める | LLM に頼む |
|---|---|
| 献立を組む、理由を付ける | 書き込み（話し言葉）の読み取りだけ |
| 除外・アレルゲンの判定、「要確認」 | |
| 人数と分量、パック単位の丸め、買い物リスト | |

- LLM がなくても全部動く。書き込みはルールベース（`parseMessage`）でも読み取る。
- LLM の読み取り結果は、必ずエンジンの `validateCommands` で検証してから使う（マスタにない食材・料理、ありえない日付は捨てる）。1件も残らなければルールベースに戻る。
- LLM の出力の形は、ルールベースと同じ命令に、欠席の取り消し（`cancel`）・在庫の質問（`question`）・冷凍（`frozen`）の印を足したもの。過ぎた日のこと・打ち消し・仮定の文では、献立を変える命令を出さないように頼んでいる（出さなければルールベースが読む）。
- 家族のニックネームは送らない。本文の名前を、ひらがな・カタカナ・全角半角・大文字小文字の書き分けも含めて `member_1` などの id に置き換え、メンバーは id・年齢帯・続柄だけを渡す（画面とサーバーで同じ決まり）。1文字の名前は、かなでないとき（漢字・英字など）だけ置き換える（かな1文字はほかの言葉の一部を壊しやすく、エンジンも名前として読まない）。
- 「明日」「水曜」などの日付はモデルに計算させない。今日から14日分の日付と曜日の表を渡し、そこから選ばせる。

### AI の読み取り

- **Artifact の中**（`npm run build:artifact` のページを claude.ai で公開したとき）：見ている人の Claude を使う（`window.claude.use('sample')`）。公開するときに、ページの機能（capabilities）として `sample` を宣言する（`{ "sample": {} }`）。宣言がないと AI は使えず、ルールベースだけで読み取る。初回に許可を求められる。使えないとき・許可しないときも、ルールベースで動く。
- **画面の設定**：「家族と設定」の「AI の読み取り」で、おまかせ（ルールで読めないときだけ AI。既定）・いつも AI・使わない を選ぶ。読み取り中は［翌日へ進む］を押せない。読み取りの間にリセット・読み込み・はじめから設定などで家族やデータが入れ替わったら、その結果は使わない（そう知らせる）。
- **開発時**：サーバーの `.env` に `PARSE_API_ENABLED=1` を書いて `npm run server` で起動し、画面の `.env.local` などで `VITE_PARSE_API=http://127.0.0.1:8787/api/parse` を設定すると、画面がサーバーの `/api/parse` を使う。
- **サーバー**：`ANTHROPIC_API_KEY` があるときだけ LLM を使う。モデルは `KIMETOKU_MODEL`（既定 `claude-opus-5-5`）。1回の読み取りは12秒まで（再試行を含む）。キーがない、間に合わない、断られた、失敗したときはルールベースで読む（理由はログに出す。本文は出さない）。

`/api/parse` は開発用の口で、認証がない。`ANTHROPIC_API_KEY` があると、呼ばれるたびに LLM の費用がかかる。そのため次のようにしている。

- 既定では使えない（404）。`PARSE_API_ENABLED=1` のときだけ使える。公開するサーバー（LINE の webhook を受けるもの）では有効にしない。
- 有効にしたときは、`HOST` を設定しなければ 127.0.0.1（このマシンからだけ）で待ち受ける。
- `CORS_ORIGIN` にないオリジンのページからは 403、本文が JSON（`application/json`）でないもの（ほかのサイトのフォームなど）は 415 で、LLM を呼ぶ前に断る。
- 断られたときや、サーバーが動いていないとき、画面はルールベースで読む。

`POST /api/parse` の形：

```jsonc
// リクエスト
{ "text": "@きめとく 水曜は夫が飲み会", "today": "2026-11-09", "members": [/* Member[] */] }
// レスポンス（commands は validateCommands 済み）
{ "commands": [{ "type": "absence", "date": "2026-11-11", "memberRef": "member_2" }], "source": "llm" }
```

## LINE で動かすには

1. LINE Developers で Messaging API のチャネルを作る。
2. `.env` に `LINE_CHANNEL_SECRET`（署名の検証）と `LINE_CHANNEL_ACCESS_TOKEN`（返信・配信）を書き、`npm run server` で起動する。
3. サーバーを公開できる URL に置き、チャネルの webhook の URL を `https://<公開URL>/line/webhook` にする（webhook の利用をオン、自動の応答メッセージはオフ、グループへの参加を許可）。公開するサーバーでは `PARSE_API_ENABLED` を設定しない（上の「AI の読み取り」）。
4. 1対1のトークでは、書き込みをすべて読む。グループでは「@きめとく」で始めるか、bot をメンションした発言だけを読む（それ以外は保存もしない）。
5. 夕方の配信（有料版の「今日はこれ」、来週の献立、解凍の連絡）は、外部のスケジューラから毎日（土日も）17:00 ごろに `POST /cron/evening` を呼ぶ。`Authorization: Bearer <CRON_SECRET>` が必要。来週の献立は最初の買い物日の前日（土日のこともある）にできるので、平日だけ呼ぶと、週末にできた献立は月曜の配信になる（終わった週の振り返りの一文は付かない）。配信の文面は、送るときの献立で作る。
   ただし試作版では、LINE の世帯はデモの家族（無料版）で作り、有料版に切り替える方法がない。そのため、いまは LINE で配信は届かない（有料版の配信は、画面のデモで試せる）。

- 友だち追加・グループ参加のとき、デモの家族の状態を作る（試作版の制限）。
- 保存するのは、送り元（ユーザー・グループ）ごとの献立・在庫・記録・買い物リストと bot の返事、LINE の ID（`DATA_DIR` の JSON ファイル）。発言の原文は保存しない（1対1でも）。
- ブロック（友だち解除）・グループからの退出で、その送り元の記録を消す。また追加されたら、新しく作る。それまでは記録を残す（31日より長く間が空いた記録は、次に使ったときにデモの家族で作り直す）。
- ボタンは、返信の最後のメッセージのクイックリプライ（13個まで）に並ぶ。同じ名前のボタンが2つ以上のメッセージにあるときは日付を付ける（今日の分には付けない。例：提案が2つなら「11/10(火) 替える」「11/12(木) 替える」）。同じ返信の中で、あとの提案に置き換わった提案のボタンは出さない（押しても使えないため）。
- リッチメニューと LIFF は含まない。
- 署名（`x-line-signature`）は必ず検証する。返信は reply API を使う。
- そのほかの環境変数（`DATA_DIR`、`PORT`、`HOST`、`PARSE_API_ENABLED`、`CORS_ORIGIN` など）は [.env.example](.env.example) を参照。

## 安全について

- アレルギーの判定は除外の補助（参考）であり、安全を保証するものではない。この一文は画面にも出す。
- 重い食物アレルギー（アナフィラキシーの経験など）は、このプロトタイプの対象外。印を付けると、対象外である旨の注意を出す。
- 判定は、その日に食べるメンバー（乳児を除く）の除外条件で行う。食材の派生原材料（醤油の小麦・大豆、マヨネーズの卵 など）も含める。
  - 除外のある人が欠席の日は、その人の除外を外して判定する。そのときは返事で知らせ、「〇曜は〇〇もいる」で元に戻せる（戻したら、その日の料理を判定し直す）。
- 自由入力の除外は、語に分けて照合する（「ピーマン、しいたけ」は両方）。
  - 「鶏肉」「えび」「甲殻類アレルギー」「卵白」などアレルゲンの名前なら、アレルゲンの除外としても扱う。
  - 「魚」「貝」「肉」「きのこ」「海藻」などの分類の語は、その種類の食材にも当てる。
  - 登録の画面では、当たる食材を見せ（当たらなければ「当たる食材はありません」）、アレルゲンの語ならアレルゲンとしての除外を先頭の候補に出す。
- ルウ・冷凍食品・惣菜・練り物などの加工品は、銘柄で原材料が違うため「要確認」とし、アレルゲンの除外がある世帯では献立に出さない（設定で出すようにしても、注意を付ける）。
- 大豆・小麦の除外は、醤油・味噌・サラダ油などの調味料にも当たるため、出せる料理がかなり少なくなる。組めない日は、その日の注意で知らせる。
- 実際に作るときは、必ず商品の原材料の表示を確かめる。消費期限を優先し、においや色で安全を判断しない。
- 1歳未満の子は献立の「食べる人」に含めない（離乳食は対象外）。はちみつを使う料理には注意を付ける。

## 制限と、今後の候補

- **覚えておく欄がない**：替える日がなかった特売（「来週の候補に入れます」）や、まだ献立のない日（来週など）の欠席を覚えておく欄が `AppState` にない。いまは、献立ができてからもう一度伝えてもらう。特売の食材は「〇〇買った」で在庫に入れれば、日持ちするあいだは献立に使う。
- **在庫はおおまか**：在庫は「たっぷり／少し／なし」の3段階で、「作った」で1段階下げる。量の正確な管理はしない。
- **家族の反応**：無料版は世帯として、有料版はメンバーごとに◎○△を記録する。子どもの2択の投票はまだない。
- **定番の編集**：家族と設定に「うちの定番」の一覧を出すが、追加・削除の画面はまだない（名前だけの定番を作る・消すための公開APIがない。エンジンの customDish は index.ts から出しておらず、isFavorite は customDishes をすべて定番とみなす）。定番は初回設定で選ぶ。
- **トークの古いカード**：カードは送った時点の献立を持たず、いまの献立で描く（古いカードは畳む）。送った時点を正確に残すなら、カードに料理の写しを持たせる（types.ts の契約の変更）。
- **LINE**：友だち追加・グループ参加でデモの家族の状態を作る（試作版。家族を設定する LIFF の画面はない）。リッチメニューもない。
- **作らないもの**（DESIGN.md 1章）：本物の課金、ネイティブアプリ、写真からの在庫登録、特売データの連携、栄養の数値。
- **今後**：お弁当への取り分け、カレーの甘口の取り分け、ネット注文との連携、高齢の親・単身・健康目標などへの対応は、企画の後の段階（[../docs/app-proposal.md](../docs/app-proposal.md)）。
